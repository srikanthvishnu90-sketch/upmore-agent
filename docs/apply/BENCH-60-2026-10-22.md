## Binding constraint (measured, with the mechanism)

**Chromium page/target crashes under memory pressure on this host
(8 GB RAM, 2 vCPU, no swap).** Free RAM sat at ~160–170 MB through the
bench with ~80–111 Chromium processes resident. The crash signature
is verbatim from the legs' board-call records:
`elementHandle.evaluate: Target crashed`, `page.evaluate: Target
crashed`, `browser.newContext: Target page, context or browser has
been closed`. Crash yield grew as crashed pages and unreaped sessions
accumulated (2 crashes in slice 1 → 23 in slice 2). Two amplifiers,
both measured tonight:

1. **Zombie sessions**: a session whose page crashed stays "live" in
   the board service until the 10-minute idle TTL reaps it. Under a
   crash storm the per-user session cap (64 total; ceil(64/shards)
   per shard) fills with zombies → new creates refused
   **409 SESSION_LIMIT** (×8 proven by raw probe in pre-flight) → the
   bridge wrapper returns null → 155 stops the application
   **BOARD_NOT_WIRED** (×4 in-bench, all late, 0 board calls).
2. **No recovery of the run record**: when a board call throws
   mid-drive, the throw escapes 155's per-application stop handling;
   the executor blocks the whole intent `DRIVER_ERROR` and NO run
   record is saved (48 legs) — one crashed page erases the batch's
   entire record for that intent (F-036).

What lifts it, in order of leverage: (a) more RAM/vCPU on the worker
host (the 2-vCPU ceiling chunk 70 named, now joined by RAM); (b)
reap-on-crash in the board service — a session whose page died should
free its slot immediately, not at TTL; (c) the F-036 catch so a
crashed drive still lands a named per-application outcome + run
record; (d) F-035's refusal reason propagation so saturation stops
name themselves. None of these were built tonight (one-fix discipline;
the bench's job was to measure).
