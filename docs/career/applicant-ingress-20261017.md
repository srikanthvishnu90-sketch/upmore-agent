# Applicant ingress — source-only continuation

No existing file-upload ingress was found in the career handler/app/function source. The new standalone `supabase/functions/career-applicant/index.ts` uses verified Supabase Auth identity and the existing backend RPC credentials, without editing agent-chat, onboarding, native conversation or native browser files. Nothing is deployed or credential-bound.

The handler reuses `CareerProfile.createProfile` from the existing career bundle for canonical defaults and the existing identity redactor for explicit field values; it does not create a second profile model or store prohibited identity/code/password text as a confirmed field.

The source API has three distinct steps:

- `POST /uploads`: multipart `threadId`, `requestId`, one original PDF/DOCX `file`, and optional `filename` declaration to preserve quotes exactly across multipart header encoding. The declaration must match the file header’s safe serialization; no arbitrary percent decoding occurs. The server validates an authenticated owner before bounded body parsing; it preserves bytes and creates an unconfirmed owned upload. File text never becomes applicant facts.
- `POST /review`: JSON `threadId`, `uploadId`, `fields`. Only explicit supported standard text fields may appear. The response binds owned upload metadata, account version/epoch, thread and exact fields to a server review hash. No field is confirmed by this read.
- `POST /confirm`: JSON `threadId`, `requestId`, `uploadId`, `reviewHash`, `fields`, `message`. Resume-only confirmation requires `use this resume`; confirming any field additionally requires `use this resume and confirm these fields`. Both require the exact owned upload/review reference. A bare phrase without those references, generic yes, extracted page text, or a client owner ID is rejected.

Shared `career_applicant_ingress.js` is used directly by the actual Deno entry. Tests execute that entry graph with synthetic Auth identity and local SQL transport; no fixture handler stands in for it. Request hashes cover the exact typed action and its metadata. Unknown write outcomes are unavailable and tell the client to reuse the same request ID; the handler never retries a write automatically.

`career_applicant_format.js` validates a bounded plain PDF/DOCX container, MIME, extension, filename, size, ZIP structure/CRC and expansion budget. It never rewrites bytes or extracts profile facts. The PDF pilot dialect requires traditional xref tables and refuses encrypted/active-content forms; DOCX refuses encrypted/macro/embedded-object/DTD forms. Unsupported documents return an explicit format refusal. This is container validation, not a full PDF/OOXML semantic validator or malware certification. The file limit is 1 MiB; decompression is bounded. Node-compatible zlib is [documented by Deno](https://docs.deno.com/api/node/zlib/); the earlier browser executor had no Deno binary. The integration executor later passed actual-entry Deno checking and exact-head Deno CI; a real deployed Edge/Auth invocation remains unverified.

The forward proposal `supabase/sql/proposals/career_applicant_ingress_v1.sql` is now tested on isolated PostgreSQL. It reuses `career_host_commit`, the existing account version/epoch/owner lock, original immutable resume table and task-lease reader. It adds owned unconfirmed staging and a review record, then atomically commits the real confirmation message, canonical profile fields, their provenance and the immutable confirmed bytes. The byte staging copy is cleared on confirmation; correction makes a new immutable version. A late insert failure rolls back the turn/profile/account changes together.

Field records contain source thread, turn key, exact typed request hash, owned upload ID, review hash and canonical profile path. Reads suppress fields whose source-profile values were subsequently corrected. Because existing canonical profiles are per thread, fields are returned only for a task in the confirmed source thread; another owned thread must explicitly review/confirm those values there. There is no invented global latest-profile merge. Resume bytes remain owner/epoch scoped.

Unconfirmed uploads expire for access after 15 minutes; four active drafts and twenty confirmed versions per owner are the bounded pilot limits. Authenticated valid requests commit owner-scoped expired-byte cleanup separately, so a later refusal cannot roll that cleanup back. STOP denies review/confirmation/read, and ERASE removes both unconfirmed uploads and confirmed records for that owner. A backend `career_applicant_upload_sweep_v1(user,limit)` call is provided and tested. **Idle physical cleanup still requires an operator-integrated schedule**; no cron, resource or job was provisioned. Access expiry is enforced even before physical sweeping. Durable confirmed documents remain until owner erasure; backups follow the existing retention policy.

The ingress unit tests execute the actual standalone entry graph with synthetic Auth and backend failures. PostgreSQL tests use that same entry, actual SQL functions and real task leases, with synthetic applicant records. The earlier browser checkpoint reported 28 PostgreSQL cases and nine entry/format cases; those are historical, not final integration verification. The [independent-review follow-up](critical-repairs/native-browser-compatibility-v1/INDEPENDENT-REVIEW-FOLLOWUP.md) records fresh results and frozen gaps. The endpoint fails closed without its RPCs. The original resume-store proposal remains unapplied. No live user resume, application or employer receipt is represented by these source/unit checks.


Lease review follow-up: a real lock holder delayed the resolver past its owned lease deadline. Before the repair the regression failed with “Missing expected rejection”; after switching the post-lock expiry checks to `clock_timestamp()` it passes. This is an isolated source-level reproduction, not an observed live exploit. The runner also waits beyond the PostgreSQL image's temporary initialization server before loading schemas.

Deployment remains unperformed. The client must call these documented routes with an actual owner JWT, stable request IDs and the server-issued review hash; no application UI was changed. The CORS allowlist, actual Edge/Deno compatibility, migrations and idle cleanup schedule require owner/Muse integration. None is guessed or enabled here. Resume/field confirmation creates no employer approval, task submission or external registration.


Integration review also applies the existing identity policy to filename metadata before storage and inspects declared XML content types regardless of ZIP filename suffix, including settings.dat. XML parts require UTF-8/ASCII; unsupported encoded Content-Type metadata is refused. Original allowed bytes are preserved. These checks remain a bounded container policy, not full OOXML/malware certification.
