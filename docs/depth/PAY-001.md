# Depth protocol: PAY-001, send to a saved recipient

Owner: Claude. Status words: planned, built, proven (its test fails under the planted break and passes without it).

Why first: this is where a wrong, double or unauthorized action loses the user's money with no undo on most rails. Every other capability can be corrected later; a Venmo send to the wrong handle cannot.

Scope: the user says "send $40 to Sarah for dinner" and money leaves. The saved-recipient path only; a first-time recipient is PAY-002 and is out of scope here except where PAY-001 must refuse to treat a stranger as saved. Rails: handoff rails (Venmo, Zelle, Cash App, PayPal) where the user taps and the agent stages and watches; partner rails (ACH) where the agent writes through a live partner. Live partners stay gated; the tests run the full lifecycle on a fake rail through the real operating model.

Files: `packages/domain/64-agent-send.js` (the dialogue and state machine over AgentMoney, AgentLoop, AgentVoice, DataGuard and AgentControl), `tests/depth-PAY-001.test.cjs` (one test per sub-capability, tagged `[S01]` to `[S15]`, plus the adversarial log `[ADV]`), `evals/depth/PAY-001.mutations.cjs` (one planted defect per sub-capability), `evals/depth/run.cjs` (applies each defect to a copy of the domain, proves the tagged test fails, restores, proves all pass).

Check: `node --test tests/depth-PAY-001.test.cjs && node evals/depth/run.cjs PAY-001`

## The 15 sub-capabilities (enumerated before implementation)

Each is a behavior the user can observe in the conversation or in their account, not an internal property.

| # | Sub-capability | What the user sees |
| --- | --- | --- |
| S01 | Missing amount asks | "send Sarah" gets "How much?"; nothing is staged, no confirmation is offered. |
| S02 | Amounts parse exactly | "$40", "40", "40.50", "1,800", "$1.8k" and whole-dollar words ("forty bucks", owner's megadoc A12) become the exact cents, shown as numerals on the card; "0" asks instead of guessing; a number inside the memo is never taken as the amount. |
| S03 | Saved recipient resolves, ambiguity asks | Full name, first name, alias or handle resolves to one saved person; two matches get "Which Marcus: Marcus L (@marcus) or Marcus T?" and nothing is staged until the user picks. |
| S04 | Strangers and look-alikes never pass as saved | An unknown name gets the new-recipient ask (PAY-002, confirmed in full); a handle within two edits of a saved handle is named as a possible look-alike before anything is staged. |
| S05 | Free rail first, fees and timing shown | The rail chosen is the free one the recipient can receive on; the comparison lists each rail's fee and timing; a gated partner rail is never offered as if live; "instant" is a stated option, not a default. |
| S06 | Confirmation restates five fields, nothing written before yes | Action, exact amount, recipient with handle, funding account, fee (or "no fee") and timing appear in one confirmation; the rail has received zero writes at that point. |
| S07 | Plain yes approves, qualified yes corrects | "yes" executes the pending action exactly; "yes but make it $40" is a correction: the old proposal is dropped, the corrected one is re-confirmed, and nothing has been written. |
| S08 | No means nothing changed | "no", "stop", "never mind" clear the pending action; the reply says nothing was changed; no write. |
| S09 | Stale approval is not approval | A yes after the card expires (10 minutes) is refused with the reason; no write; a fresh card is re-offered for a fresh yes (spec 16 item 4, response-style corpus 2.09). |
| S10 | Same instruction twice means once | The same send (recipient, amount, day) delivered twice produces one write; the second reply says it was already done and names the reference. |
| S11 | Crash between write and receipt never double-sends | If the process dies after the rail accepted the write, the next wake reconciles by reading back; one write; the receipt still arrives. |
| S12 | Timeouts are unknown, rejections are failures | A rail timeout yields "unknown", no blind retry, a scheduled follow-up that later confirms; a rail rejection yields "failed" with the rail's reason, nothing posted, and the next step. |
| S13 | Scam and injection stop before the confirmation | A memo or instruction matching a scam pattern stops with the phrase named; instruction-like text in a memo is treated as text and never changes the amount or recipient. |
| S14 | Limits and the kill switch hold | Over the daily or weekly limit stops with the limit named and cannot be raised from a message; while the kill switch is on, a send is blocked without even asking. |
| S15 | Receipts only after the rail confirms; staging is never "sent" | A partner-rail receipt carries amount, recipient, rail, reference and the reversal contract, only after verification; a handoff rail says "staged, you tap" with the steps, and reports "landed" only when the debit posts. |
| S16 | Stop-on-change | Between the yes and the send, the send is prepared again from the same words; a changed rail, fee, amount or recipient, or a limit that now stops it, sends nothing and puts up a fresh card. Added 2026-10-11 with the two-segment card. |

## The three worst failures with real money or trust, and what guards each

1. **Money reaches the wrong person.** A look-alike handle, an ambiguous first name, or a stranger treated as saved. On Venmo, Zelle and Cash App that money is gone. Guards: S03 (ambiguity asks, never picks), S04 (strangers routed to the full-confirmation path, look-alike handles named), S06 (the handle is restated in the confirmation).
2. **The same money leaves twice.** A duplicate webhook, a retry after a timeout, a crash after the rail accepted the write. Guards: S10 (one key per send per day, "already done"), S11 (reconcile by read-back after a crash), S12 (unknown is never retried blind).
3. **Money leaves without a real decision by the user.** An injected instruction in a memo, a scam script, a stale approval, a "yes, but" read as yes, a limit raised from a message, an action while paused. Guards: S13 (scam stop, memo as data), S09 (expiry), S07 (qualified yes is a correction), S14 (limits and the kill switch), S08 (no is honored).
