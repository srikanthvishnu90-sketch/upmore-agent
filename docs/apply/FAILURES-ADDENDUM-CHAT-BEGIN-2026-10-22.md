## MUSE-F-030 — FIXED (repo-only, built-not-applied): a chat/cloud begin is mis-stamped `extension`, and no DB claim ever takes a begun row

Found by the chunk-40% map (docs/career/chat-begin-caller-2026-10-22.md,
links 6-7), read-only, from the migration sources on
`origin/wo/first-real-submission`:

- `career_apply_extension_begin_own` (latest definition, migration
  20261021120000, line 12) refuses any payload whose `source` is not
  the literal `'extension'`, and (line 19) stamps the job row
  `source = 'extension'`. Any begin through
  `career_apply_extension_begin_agent_own` — including a begin the
  CHAT path makes on behalf of the cloud worker — is therefore
  recorded as an extension application by construction.
- The family gate counts hand submissions per portal from
  email-confirmed rows with source `own_computer` or `extension`
  (migration 20261021075000). A cloud-driven application begun from
  chat would, once email-confirmed, count toward the gate's HAND
  tally — provenance the gate's whole design depends on, corrupted
  by a label.
- Compounding: `career_apply_cloud_claim_at` (migration
  20261021080000) claims only `state = 'queued' AND source IS NULL
  AND approval_hash = payload_hash` rows. A begun row is `driving` /
  `extension` (pre-claimed by begin_own for its beginner-driver), so
  the DB cloud claim never takes it: in production today there is no
  DB path from a begun row to a cloud drive. (The TEST-world executor
  drives from the stored batch record, not from this row.)

Fix shape (its own round; needs a migration, which is the owner's
word): a begin variant for the agent path that takes an explicit
driver source (`cloud`) and leaves the row claimable by the cloud
claim — or a cloud claim branch for agent-begun rows — plus the gate
tally reading only true hand sources. NOT built here: chunk 40% is
repo-only under the owner's 2026-10-22 00:06 ruling, and a migration
is a live apply.

Resolution (2026-10-22, branch `muse/2026-10-22-chat-begin-caller`,
root-cause note `docs/apply/ROOT-CAUSE-F030-BEGIN-CLAIM-2026-10-22.md`):
shape (a), the sibling door — the claim predicate and the gate were
never widened, because both were correct; the stamp was the defect.

- Migration `20261024140000_career_apply_agent_cloud_begin.sql`
  (repo only, NOT applied anywhere): the WO-102 start checks move
  verbatim (byte-identical, mechanically extracted) into the internal
  helper `career_apply_agent_contract_approval` (granted to no one);
  `career_apply_extension_begin_agent_own` is redefined over it with
  its tail byte-identical, so the extension door is unchanged; the new
  `career_apply_cloud_begin_agent_own` runs the same helper, then its
  door checks (`source = 'cloud'`, `destination` ^https://,
  `engine_approval` 64 hex — the shapes `career_apply_cloud_refusal`
  demands at claim time), then only ENQUEUES (queued, source null,
  attempts 0, no lease) and stamps `agent_batch_hash`. The claim
  stamps the row `'cloud'` itself, once, from queued — so a chat
  submission can never enter the gate's hand tally, and neither the
  claim nor the gate function needed any change.
- Module 176: `door: "cloud"` builds the cloud payload (source
  `'cloud'`, the entry's destination + engine approval) and calls the
  new RPC; the door's three refusals are mirrored locally with the
  DB's messages; the default door is byte-identical to before.
  `router_core.career.js` regenerated by the standard build.
- Proof: `tests/career-agent-begin-cloud.test.cjs` 11/11 (payload,
  door mirror, flag-OFF zero-RPC, verbatim DB refusal, and a
  begin → claim leg modeled on the claim's cited predicates: claimed
  once as `'cloud'`, never twice; an extension-begun row is never

  (begin → queued row → gate opens on the tester's 3 hand submissions
