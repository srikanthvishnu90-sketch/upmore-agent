# Exact batch approval and independent role continuation

This is a tested backend source checkpoint. It adds `career-batch/index.ts`, its authenticated command handler and an unapplied `career_application_batch_v1.sql` proposal. Normal `POST {thread_id,turn_key,message}` and native generation/checker accounting are unchanged. No endpoint has been deployed and no live schema has been changed.

The endpoint accepts `{threadId, requestId, action, input}`. Auth uses the existing server `getUser` pattern; the verified owner never comes from the client body. Actions are `create`, `status`, `review`, `approve`, `answers` and `reconcile`. Configured origins support the public `apikey` header used by the app; the same missing-header preflight defect was corrected narrowly in applicant ingress, preserving its origin list, Auth and file validation.

`create` takes 1–100 distinct existing owned task IDs from the same thread. Their server-held preparations supply posting and original artifact references. It queues fresh preparation through the existing task-intent ledger, while admitted or uncertain tasks remain fenced. These are selected references, not a claim of 100 suitable openings or 100 submissions.

`status` derives each role's progress from durable task results and effects. A blocked role occupies its own row and does not prevent healthy roles from advancing. Workflow commands leave the shared account version unchanged; a role answer does not invalidate another role's unchanged approval. Genuine shared-profile corrections still stale the entire batch. Erase deletes private batch reviews, answers and command receipts; pause, stale context and foreign owners remain denied.

Batch preparation requires an owned resolver to provide `careerProfile`, `scoringProfile` and `currentPosting:{posting,observedAt,sourceSha256}` under the existing owner/version/epoch scope. It reuses121/132 eligibility and151 fact citations. Closed postings stop before opening a browser; changed job content requires review. Missing current eligibility or fact evidence fails closed. Existing contact-only equipment does not satisfy this contract. The legacy direct single-task preparation path still needs the broader eligibility composition; this checkpoint does not claim that gap closed.

`review` resolves current owned worker reviews and freezes job IDs/URLs, exact payload, original resume hash/version, profile hash, current eligibility evidence and observed question-wording hashes. It lists held roles separately. `approve` requires the returned literal `Approve batch <reviewHash>`. The manifest uses opaque `postgres-jsonb-text/v1` hashing; clients display the server result rather than reconstructing it. Every included role must still match. One changed role rolls back all new approval intents in that command. Held roles, future jobs and changed payloads receive no authority from the old manifest. Review and execution-grant expiry remain ten minutes.

`answers` accepts only explicit scalar values for observed required questions on one waiting role. It requires the exact question-set hash, each field hash and the returned task identity in `Confirm answers for <taskId> <questionsHash>`. Values stay scoped to that role; they do not become master-profile facts. Existing confirmed equipment facts are reused without re-asking. The worker compares actual current field wording before filling. Changed wording discards the old value and asks again. Answer confirmation queues preparation and authorizes no submission; the resulting exact application needs a fresh review and approval.

`reconcile` uses the existing readback-only task action with `Reconcile batch role <taskId>`. It grants no submit authority. After any admitted submit, neither a new batch nor lost local checkpoints can create another submit. Missing authoritative proof remains unknown. Current real-employer readback remains unavailable; the selected public employer route has a human challenge and an unsupported adapter, recorded in [SELECTED-POSTING.md](SELECTED-POSTING.md).

Every mutating command has an immutable owner/request receipt. Lost acknowledgements retry the identical request ID/body; changed reuse conflicts. Progress reads are fresh SQL lookups rather than replayed command acknowledgements. Existing shared15/day,5/vendor/day and1/company/30-day admission limits still apply atomically at dispatch.

Rollout prerequisites, owned by Muse: apply the admissions and batch proposals after owned-claim recovery, truthfully reconcile/backfill any pre-existing submit effects, configure the existing Auth/origin bindings, supply the owned eligibility resolver, and verify the packaged worker on an authorized normal-sandbox runtime. These steps were not performed. No credential was read or changed.

Remaining product work includes ordinary-text discovery/selection into this API, app batch cards/answer controls, confirmed-resume metadata restoration, fuller career-fact confirmation, bounded parallel scheduling/backoff, multi-day grant/review rehydration and throughput reporting. Existing fifteen-minute worker-private retention remains. The durable SQL rows do not silently renew expired authority or create a second matching/execution engine.

Validation uses the actual Edge entry, real isolated PostgreSQL and existing worker, with an explicitly synthetic board returning only UNKNOWN. It proves command plumbing, atomicity and fencing; it manufactures no employer receipt and proves no live-model quality. See [batch-evidence.json](batch-evidence.json) for exact hashes, failures, completed checks and pending broad validation.
