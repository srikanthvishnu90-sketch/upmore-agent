## 1. Demand math at 96,000 users

**Utilization definition:** the share of the 96,000 users who submit at the full 15/day cap on a given day. (Users below cap scale linearly — halve the actives, halve everything.)

Applications/day = 96,000 × utilization × 15:

| Utilization | Active users | Applications/day |
| --- | --- | --- |
| 100% (full cap) | 96,000 | 96,000 × 15 = **1,440,000** |
| 30% (realistic) | 28,800 | 28,800 × 15 = **432,000** |
| 10% | 9,600 | 9,600 × 15 = **144,000** |

**Drive-seconds per application, three scenarios:**

- **Scenario A — today.** 2 drives/app (prepare + approve re-drive) × 164s = **328 s/app**.
- **Scenario B — session reuse landed.** The prepare session survives to the approval drain, so 1 drive/app × 164s = **164 s/app**.
- **Scenario C — reuse + fills profiled and cut 3×.** ESTIMATE built from measured components: non-fill time (open 24.9 + form 11.7 + answers 11.1) = 47.7s; fills 122.8 ÷ 3 = 40.9s; drive = 47.7 + 40.9 = **≈89 s/app** (1 drive). The 3× is a *target*, not a measurement — where a fill's seconds actually go (page CPU vs proxy waits) is **NOT_RUN** (throughput lane), so C is the plan's hypothesis, not its promise.

**Drive-hours/day = applications/day × s/app ÷ 3,600:**

| Utilization | A — today (328s) | B — reuse (164s) | C — reuse + fills ÷3 (89s) |
| --- | --- | --- | --- |
| 100% · 1,440,000 apps | 1,440,000×328÷3600 = **131,200 h** | **65,600 h** | **35,600 h** |
| 30% · 432,000 apps | **39,360 h** | **19,680 h** | **10,680 h** |
| 10% · 144,000 apps | **13,120 h** | **6,560 h** | **3,560 h** |

Read: even in the best scenario, a full-cap day is **35,600 drive-hours** — the fleet exists to burn CPU-seconds, and per-fill time is the exchange rate. Session reuse alone halves the fleet; the fill cut nearly halves it again. Nothing else in the pipeline (feed ~5s, prepare ~6s per *batch*) appears in these numbers at all.

## 2. Fleet shape

### Concurrency model

A **slot** = one drive in flight. RAM per host: 285MB base + ~65MB/session → an 8GB host fits (8,192 − 285) ÷ 65 ≈ **121 sessions by RAM** — never the constraint. CPU is: on today's 2-vCPU host, extra concurrency bought ~nothing once saturated (pool ×4 beat pool-serial by only 3.4% on a loaded box; the host is the ceiling, not the design).

**Planning assumption (labeled, to be replaced by measurement): 1 usable slot per vCPU** at the drive's current CPU profile; the host unit below is **8 vCPU = 8 slots**. The measurement that replaces this assumption — per-drive CPU-seconds on a quiet host — was flagged NOT_RUN by both the throughput and board-session lanes and is an explicit M3 deliverable in the sequence (§4).

### Hosts required

Slots needed = drive-hours/day ÷ W, where W = the window the day's drives must clear in. **W = 6h** is the planning window (recruiting activity clusters; a user who approves at 9am cannot be quoted "sometime tonight"); W = 24h is shown as the perfect-smoothing bound nobody should plan to.

Hosts (8 slots each) at W = 6h — slots in parentheses:

| Utilization | A — today | B — reuse | C — reuse + fills ÷3 |
| --- | --- | --- | --- |
| 100% | 131,200÷6 = 21,867 slots → **2,734 hosts** | 10,934 slots → **1,367 hosts** | 5,934 slots → **742 hosts** |
| 30% | 6,560 slots → **820 hosts** | 3,280 slots → **410 hosts** | 1,780 slots → **223 hosts** |
| 10% | 2,187 slots → **274 hosts** | 1,094 slots → **137 hosts** | 594 slots → **75 hosts** |

At W = 24h every host count divides by 4 (e.g. 30%/B = 103 hosts) — that is the floor set by physics, reachable only if approvals spread perfectly across the day, which they will not.

### Queue behavior spec

- **Eligibility at enqueue.** Caps (15/day, 5/vendor/day, 1/company/30d) are checked when an intent is created; the queue never holds work that cannot legally run.
- **Fairness fence (hard prerequisite).** S-2 — the cap-ledger merge-by-record-id inside the per-user advisory lock — lands before any K>1 drain; without it, concurrent drains of one user silently drop cap records. On top of S-2, scheduling is per-user round-robin: **at most 1 drive in flight per user** (a named config knob, not a gate change), so one user's 50-batch can never occupy the fleet; global order = oldest eligible intent whose user is under their in-flight cap.
- **Autoscale trigger.** Queue depth is measured in **drive-seconds**: Q = Σ estimated drive-seconds of pending intents. Scale OUT when Q ÷ current_slots > **600s** (more than 10 minutes of queued work per slot); scale IN when Q ÷ current_slots < 60s sustained 15 minutes. A new slot joins only after passing the standing gate probes (401 / 401 / 403 / 403 + an empty drain) — a slot that fails probes never takes an intent.
- **Quoted wait.** Shown on the approval card **before** the tap (exact state before approval): `quoted_wait = (drive-seconds ahead of this batch in fairness order ÷ fleet_slots) + (this batch's drive-seconds ÷ fleet_slots)`, quoted as a rounded window and restated if the estimate slips beyond 2×.
- **Backpressure.** Batches are never silently dropped for depth: each is accepted with its quoted wait or refused *with the number* ("queue holds N drive-hours; next window ≈ T"). Unknown-outcome intents leave the queue as UNKNOWN, visibly — never re-driven (MI-115).

### Egress / IP plan

- **One attributable egress IP per host** (Fly.io: dedicated IPv4 $2/mo, price in §3; VM hosts: the host's primary IPv4). Per-IP budgets are only meaningful if an IP maps to a known set of board processes — per-process IPs inside a host are not planned.
- **Per-family, per-IP daily drive budgets are OPEN QUESTIONS for every family.** No board's rate limit has been measured — not Greenhouse's, not anyone's — and this plan invents none. The measurement that closes it: a controlled ramp per family during the first live batches, recording throttle/block signals against drives/IP/day, per family. Until a family has a measured budget, pacing is set by board config at the most conservative observed-clean rate and every throttle signal is a ledger event.
- **What is already measured:** eligibility is not an egress problem — the §6.3 host gate refuses employer wrapper URLs at session creation (29 of 91 in the census family slice) regardless of which IP asks. Family coverage order stands: Greenhouse (driveable today) → Lever → Ashby → Workday verdicts.

## 3. Hosting decision

### Requirements (any host class must meet all four before it joins the fleet)

1. **Sandbox-capable Chromium.** Today's host runs with the recorded opt-out `UPMORE_CHROMIUM_SANDBOX=off` because this VM class cannot run sandboxed Chromium. That posture does not scale: a fleet driving employer forms for 96K users runs Chromium **with** its sandbox on. Proof required per host class — a sandbox-on drive smoke in the gate-probe suite — never assumed from a vendor page.
2. **Auto-restore (F8).** Worker units are code, not hand-restored state: image + boot-time unit registration + watchdog. A wiped or replaced host re-forms and passes gate probes with **zero human steps**. Today's baseline is a ~10-minute *human* restore, needed twice in one day.
3. **Programmatic provisioning.** The autoscale trigger (§2) needs an API that creates/destroys hosts in minutes and reports them healthy only after probes pass.
4. **Attributable egress.** One public IPv4 per host (§2), so per-family pacing and throttle signals have an owner.

### Recommendation

**Default fleet: plain dedicated-vCPU VMs (Hetzner CCX class).** Cheapest measured cost per slot by ~7×, full kernels (the sandbox-on proof is straightforward), API provisioning exists. **Fly Machines as the burst valve**: per-second billing wins for short queue spikes, new-region spin-up, and as the second source if VM stock runs dry — *if* the sandbox-on proof passes on Firecracker. The deciding artifacts are the two proofs (sandbox-on drive smoke; F8 kill-and-replace drill), not the price table: run both on both host classes before the 1K step (§4) and let the results, not this document, make the final call.

## 4. The sequence — which bottleneck falls at each order of magnitude

**100 users — drive correctness falls first.** Capacity is a non-issue (100 users at full cap = 1,500 apps/day × 328s ≈ 137 drive-hours ≈ 23 slots ≈ 3 hosts). What actually stops the product: real-profile drives stop at `ANSWER_OBSERVATION_MISMATCH` / `UNCOVERED_QUESTION` (F-007 class) — with the real profile the harness produced **0 doorsteps**. *Proof artifact:* the first employer-confirmed submission + receipt (the O1/M4 artifact), plus a drive-completion report on real profiles naming every stop.

**1,000 users — serialization and host fragility fall.** One board process globally (27.9s probe latency during a drive) and worker units wiped twice in a day are the binding facts. Falls when: parallel board processes exist behind S-2 + S-1 (O5 M3), the keep-warm pool gate removes per-drive launches, and F8 auto-restore makes the fleet self-healing on a durable host class (§3 proofs run here). *Proof artifacts:* an observed parallel drain (two drives in flight, cap ledger verified intact, zero records lost) and a timed kill-drill record — host replaced → fleet re-formed, gates green, 0 human steps.

**10,000 users — per-fill time falls.** Fills are ~72% of every drive; slot count, and therefore fleet cost, is a linear function of fill seconds. At 10K users/30% (3,000 actives × 15 = 45,000 apps/day), scenario B = 45,000 × 164s ÷ 3,600 ≈ 2,050 drive-hours/day ≈ 342 slots ≈ 43 hosts — affordable iron; what must fall is the *rate*: per-fill profiling (where the 16–28s goes — page CPU vs proxy waits, today NOT_RUN) and the 3× cut that defines scenario C, plus the S-2 fairness fence proven under real multi-user contention. *Proof artifacts:* the per-fill profile report with before/after drive medians on real forms, and a fairness test record (two users' batches interleaved; both cap ledgers verified).

**96,000 users — fleet economics and egress fall.** The scenario spread at 30% is 820 → 223 hosts (A → C): the difference between a viable and an unviable fleet is entirely drive CPU-seconds. And the one term no amount of hosts fixes: **per-IP, per-family board limits are unmeasured** — if a family throttles below fleet capacity, throughput for that family is capped by the board, not by us. *Proof artifacts:* a 96K-shape synthetic load test (intents at the 96K × 30% profile; quoted waits vs actuals reported), the per-family ramp measurements (drives/IP/day vs throttle signals, per family), and one real monthly bill reconciled against §3's model.
