# ROOT CAUSE — MUSE-F-025: EMPTY_FORM open race (2026-10-22)

## The defect (one line)

A healthy posting is stopped `EMPTY_FORM` ("zero fillable fields") because the
form is read exactly ONCE, at an instant that can land before the board's
single-page application form has mounted; no layer ever re-reads.

## Live evidence (primary record)

- `~/workspace/lane-b-status.md` (WIDGET-ATTACH host application, 2026-10-21
  22:49–23:00 CDT): live re-prepare `batch-7ac6d3b30fa5` stopped `EMPTY_FORM`
  ×2 (both Palantir postings), recorded there as "page-timing race in open's
  single post-apply-click discover; bracketed by direct drives returning
  27/34 fields through the same service+bridge — transient, named".
- FDSE-MISMATCH lane entry, same file: "F-025 EMPTY_FORM open race OPEN".
- Audit row (`docs/apply/AUDIT-INITIAL-WRONGS-2026-10-22.md`): the stop fired
  in ~100 ms; not reproduced in any later drive; no fix landed.
- The bracketing drives are the discriminator: same postings, same service,
  same bridge returned 27 and 34 fields minutes apart. The form existed; the
  read was early. This is a timing defect, not a missing-form defect.

## The exact code path (base cbcd0141)

1. `packages/domain/149-career-portal-apply.js`, `prepareRound`, line 796:
   `const formDef = board.form();` — the ONLY form read before the verdict.
2. Same function, lines 804–807: if `formDef.fields` is empty,
   `logStep("empty_form_stop", { fieldCount: 0 })` and
   `return blocked("EMPTY_FORM", …)` — the BUG-061 zero-fields stop. The
   stop itself is deliberate and correct for a genuinely empty form (D2:
   never declare a doorstep over a form the driver never reached). The
   defect is that it consumes a single instantaneous read as final truth.
3. `packages/domain/150-career-portal-browser.js`, `form()`, line 501: one
   `call(boardId, { type: "discover" }, 30000)`. No retry, no re-issue on a
   zero-field result.
4. `scripts/career/portal-browser-helper.cjs`, `cmdDiscover`, line 251: one
   `await board.page.evaluate(fnDiscoverFields)`. Whatever the DOM holds at
   that instant is the answer.
5. Upstream, `cmdOpen` (same helper) settles a fixed ~1200 ms after
   domcontentloaded and, after an apply click, a fixed 800 ms (line 216)
   before its own single discover. Those fixed settles are the entire
   defence against a slow first paint today — when the SPA form component
   mounts after them, every subsequent read in the chain is still a single
   snapshot, and the first one 149 takes decides the run.

Why the read can be empty on a healthy page: Lever/Greenhouse application
forms are client-rendered. After navigation (and after the apply click) the
page shell paints first and the form component mounts asynchronously. A
discover evaluate executed in that gap legitimately returns `[]` — the DOM
really has no fillable fields yet. Each layer above the helper treats that
instantaneous `[]` as the form's permanent state, and the BUG-061 guard —
written to stop doorsteps over forms that were never reached — fires on a
form that was simply not reached YET.

Deliberately out of scope: the second `board.form()` read at 149 line 575
(`buildPayload`) belongs to the doorstep/submit payload construction; it
produces no EMPTY_FORM verdict and the submit path is not touched.

## The fix shape (owner-named: a BOUNDED re-scan)

At 149's discover step — the layer that owns the verdict and the run record
(stepLog) — a zero-field read is no longer final on first sight:

- Re-read `board.form()` while it returns zero fields, up to a named finite
  bound: **5 total reads** (`EMPTY_FORM_RESCAN_MAX_READS`) and **10,000 ms
  wall-clock** (`EMPTY_FORM_RESCAN_BUDGET_MS`), whichever binds first.
  Each re-read of the browser board is a complete fresh discover
  (150 → helper `cmdDiscover` → a new evaluate on the live DOM), so the
  loop observes later paints; it is a bounded re-scan, not a sleep loop —
  there is no synthetic delay and no unbounded wait anywhere.
- Every re-read is written to the step log
  (`empty_form_rescan` per re-read; `empty_form_rescan_recovered` when a
  re-read finds fields), and the EMPTY_FORM stop itself carries a
  `rescan` record `{ reads, elapsedMs, budgetMs, maxReads, outcome }`
  (outcome `exhausted`, or `disabled` under the kill switch).
- Kill switch: `inp.emptyFormRescan === false` restores the exact single
  read (outcome `disabled`, recorded the same way).
- Unchanged: what counts as a form (`analyzeForm` / classification), every
  downstream gate, the EMPTY_FORM code and reason text, and the verdict for
  a genuinely empty form — it exhausts the bound and stops EMPTY_FORM
  exactly as today, only later and with the rescan record attached. The
  other two EMPTY_FORM sites (lines ~884, ~1005 — observation/payload
  emptiness AFTER fills) are not this defect and are not touched.

Prior art considered and NOT ported: `scripts/career/wait-primitives.cjs`
(chunk-60 event-driven fills, branch `muse/2026-10-22-event-driven-fills`
@ b8aa4106) is absent from this base tree. Its primitives wait on in-page
conditions inside the helper; this fix needs no in-page wait — pacing comes
from full discover round-trips and the bound lives at the verdict layer
where the run record is written. Porting it would add a second wait system
to paths this defect does not touch. Recorded here per the lane brief.

## Guards (BUG LAW — permanent)

`tests/career-portal-empty-form-rescan.test.cjs` (new, fail-first):

- race fake (form returns `[]` on reads 1–2, fields on read 3): base aborts
  EMPTY_FORM after 1 read; fixed proceeds past the stop, 3 reads, recovery
  recorded.
- negative control: a form that is empty on every read still stops
  EMPTY_FORM, after exactly the bounded 5 reads, outcome `exhausted`.
- boundary: fields first appearing on the 5th (last bounded) read proceed.
- fast path: fields on the first read → exactly 1 read, no rescan records
  (zero behaviour change on healthy reads).
- kill switch: `emptyFormRescan: false` → exactly 1 read, EMPTY_FORM.

These stay in the suite permanently; the negative control is the half that
keeps the BUG-061 guard honest — the re-scan may delay the EMPTY_FORM
verdict, it may never remove it.
