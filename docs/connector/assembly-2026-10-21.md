## The gate swap (package 156 — fully delegated)

The claim's entry decision is now the gate module's, at the exact
call sites its integration note
(`docs/connector/gate-integration-note-2026-10-21.md`) pins:

- `supabase/functions/agent-chat/handler-career.ts` imports
  `CareerConnectorGate` from the career bundle and computes
  `CareerConnectorGate.decide((name) => Deno.env.get(name), user.id)`
  ONCE per turn, immediately before `host.createTurnCtx(...)`,
  from the authenticated request's user id — never a channel
  bridge's resolved test id. The v1-era `CONNECTOR_ALLOWED_USER_IDS`
  parse is gone; the env contract is `CONNECTOR_ENABLED` +
  `CONNECTOR_ALLOWLIST`.
- `supabase/functions/_shared/career_host.js` carries the decision
  on the createTurnCtx literal as `ctx.connectorGate` (runtime
  only — not a STATE_KEYS entry, never snapshotted). The
  `connectorAllowlist` host dep is removed; `connectorPool` is
  unchanged.
- `packages/domain/142-career-router.js` req-loads 156-159 at its
  head (fail-soft, design SS2), consults `c.connectorGate` in
  dispatch immediately BEFORE the `handlePeopleMatchingStop` call,
  and `handleConnector`'s first check is the decision itself (the
  inline allowlist read is deleted). An account the gate does not
  allow never reaches the claim, and the claim writes nothing
  before the check — non-allowlisted turns are byte-identical
  (guard 1), and `handlePeopleMatchingStop` is unmodified.

With neither env var set, `decide` returns `disabled` for every
user: a deploy of this tree changes no live behavior until the
owner sets both vars (checklist step order keeps it that way).

## Delegation status — the other three packages

Assembled (on the tree, bundled, req-loaded, suites green) is not
the same as delegated. Per package, honestly:

- **157 consent — NOT delegated (record-model conflict).** The
  module's canonical consent record is an append-only event log
  with chained scopes (`matched` ⊃ `introduced` ⊃ `contacted`)
  carried on the 122 profile (`profile._careerConnector`). The
  flow's live consent record is the design-note keyed record
  `{status, at, scope, version}` on the account stated-facts
  carriage — the shape the pool interface and proven guards 4/5/11
  read. Delegating means a record migration plus a pool
  re-implementation over the event log; adapting on the fly would
  fabricate event history (seq, surface) the module's own doctrine
  forbids inventing. Follow-up build, named below.
- **158 match — NOT delegated (authority conflict).** The design
  makes the pool the single authority for proposals (the F-017
  lesson: two copies of one fact diverge), with sequential states
  `awaiting_a`/`awaiting_b` — the side not yet proposed to cannot
  answer (guard 15). Module 158 is a second state authority: its
  own store + `snapshot()` persistence, symmetric answering, states
  `proposed`/`a_answered`/`both_yes`. Wiring it in means
  re-implementing the pool over 158 and re-pinning guards 7-11 +
  15 against its semantics. Follow-up build, named below.
- **159 intro — PARTIAL.** `FOLLOW_UP_AFTER_MS` is consumed at the
  fire point (the 72h duration now lives exactly once, in the
  package that owns the follow-up). `composeIntro` /
  `composeFollowUp` are NOT delegated: their templates differ from
  the monolith's intro text, and the design's assembly step 4 pins
  the intro text byte-identical (verified this assembly: the demo
  transcript regenerates byte-identical). Swapping the composition
  is a user-facing copy change — it needs the owner's/judge's
  review of 159's golden outputs first, not a silent swap.

## Drift vs the integration design (docs follow code)

- The design's wiring SS4 describes the handler parsing
  `CONNECTOR_ALLOWED_USER_IDS` into a host allowlist dep. The gate
  package's later, more specific integration note supersedes it:
  env is `CONNECTOR_ENABLED` + `CONNECTOR_ALLOWLIST`, decided per
  turn in the handler. The design's package map already assigned
  "the allowlist check" to the gate package; this assembly follows
  the map + the note.
- The design's assembly order ("monolith internals are deleted
  only as their module call replaces them, one package per
  commit") is complete for the gate only; 157/158/159 internals
  are NOT deleted, for the contract reasons above. The design
  note's step-4 bar (demo intro byte-identical) is kept.
