# F1: Web dashboard — feed, queue, tracker, receipts inline

The signed-in web app gains an Applications dashboard (chat header → "Applied", or `#careerDash`): a Feed of what actually happened, a Queue holding every application still in flight plus the prepared applications awaiting approval, and a Tracker listing every application with its true state and — on confirmed rows only — the receipt inline. Everything shown is composed from the person's own `career_apply_jobs` and `career_apply_prepared` rows: states are exactly the states the database allows, coverage reads as unreduced covered/total fractions, and a receipt appears only where the employer's confirmation email landed, with its fields copied verbatim from the row. The approval card itself is not rebuilt here: prepared queue items expose the marked slot (`data-f1-card-slot`) that the F2 card component mounts into via `TraineeDashboard.mountCards`.

## The five checks

- **(a) Real surfaces, real data only.** `src/career-dashboard.js` (`TraineeDashboard`) renders Feed / Queue / Tracker from plain record objects shaped exactly like `career_apply_jobs` / `career_apply_prepared` rows. The template wiring (`renderCareerDashboard` in `src/upmore-app-template.html`) reads those two tables for the signed-in user (owner-read RLS) and hands the rows over; no fixture prose, no mock content, nothing is rendered that a record did not say. Record text is rendered through `textContent` only (test: markup in a company name renders as text, zero injected elements). One honest boundary: the feed's batch-outcome section renders kept/dropped outcomes when a host passes them (the view-model enforces exactly-once-with-reason); the web client has no kept/dropped outcome table to read today — those outcomes are produced by the prepare path — so the shipped wiring passes the two readable models and `outcomes: []`.
- **(b) Every state shown is true.** The state vocabulary is defined once (`APPLY_STATES` / `STATE_LABELS` in `src/career-dashboard.js`) and a test parses the `career_apply_jobs` check constraint out of `supabase/migrations/20261020000001_career_apply_jobs.sql` and pins the two lists equal, in order. A lifecycle test walks one record through queued → driving → submitted_unconfirmed → confirmed and checks queue membership, tracker label, feed head and receipt gating agree at every step; an out-of-vocabulary state is refused (`unknown apply state`), never given an invented label.
- **(c) Coverage fractions, covered/total, never reduced.** Header line: Prepared · Fields filled · Confirmed, each `n/total` straight from the records. Tests pin `2/3`, `4/5`, `1/3`, a `30/60` that stays `30/60` (not `1/2`, not `50%`), and `0/0` for the empty dashboard.
- **(d) A queue of 60 in one view.** `tests/career-dashboard-dom.test.cjs` (jsdom, the repo's pinned copy) renders 60 queue rows and asserts all 60 items sit inside the single `[data-f1-single-view]` container, every job id present in the rendered text, and zero pagination controls.
- **(e) Receipts inline in the tracker.** A receipt block renders inside the confirmed row's own tracker item with company, job id, confirmation number, the full 64-character payload hash and the confirmed timestamp — byte-bound (test: mutating `confirmation_id` changes the receipt; nothing is truncated or reformatted). It exists only when `state = confirmed` AND `email_confirmed_at` is set — the product rule that the employer's email is the proof: a page-only `submitted_unconfirmed` row and a `confirmed` row without the email both render no receipt (tests pin both).

## Design (builder plan, applied exactly)

- Tokens in `src/career-dashboard.css`: `--graphite: #1E1F24`, `--silver`, and the plum as ONE token, `--accent-plum`, with `--accent-plum-light: #A58FB8`. A test asserts the token is defined exactly once and that every rule painting with it is scoped to an active state (selected tab, the in-flight `is-active` state pill, a pressed button) — plum appears nowhere else.
- **Plum value — one flag for the architect:** the brief for this lane said `#6B4F7E`, but the governing plan document's Owner decisions (Vishnu, 2026-10-22 17:09) record "The plum is `#4A2F5E`, the website's plum", so the token carries `#4A2F5E`. The one-token design makes this a one-line change if the architect rules otherwise.
- Serif headers (Georgia stack), Inter body. No connectors page exists or was added; navigation gained one button ("Applied") into the dashboard screen — connections remain inline from Profile, untouched.

## F2 integration slot

Queue items for prepared applications in `ready`/`shown` state render `<div class="f1-card-slot" data-f1-card-slot="approval-card" data-prepared-id="…">` (DOM test pins: ready + shown get slots, approved does not). `TraineeDashboard.mountCards(root, mountFn)` hands each slot and its prepared row to the host's renderer; the dashboard ships no approval UI of its own. On trunk today no prepared-row card renderer exists yet (F2 lane), so the wiring passes no `mountFn` and the slots sit empty and labeled by their data attributes only.
