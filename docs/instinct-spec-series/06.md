Upmore Spec 06: Money Movement"How can we make it pay people's owed money or rent, or send money to someone via Zelle, Venmo or other apps." This doc covers every way money leaves: P2P sends, paying people back, rent, bills, splits, requests. It starts with the honest truth about rails, because this is the domain where fake capability claims do real damage.GoalBuild src/money/: the send, request, split, rent, and bill-pay workflows, each with rail selection, confirmation UX, receipt, and a reversal or mitigation contract.The rails reality (read before building anything)Zelle has no public API. Zelle lives inside bank apps and is available to third parties only through a bank relationship. An agent cannot "just call Zelle." Path: bank-partner bill pay or Zelle through a partner bank that offers it, or the agent prepares the send and the user completes it in their bank app (handoff pattern below).Venmo and Cash App have no public send APIs for third parties. PayPal has real APIs but P2P sends via API are restricted. Path: partner rail (a money-movement provider such as Dwolla, Modern Treasury, Unit, Column, or a BaaS partner) for ACH, or the handoff pattern.Real agent-executable rails: ACH push/pull through a money-movement partner (requires the partner, KYC, and the compliance setup in doc 14), bank bill pay through a partner, and wires for large amounts.The handoff pattern is a feature, not a failure: the agent prepares everything (recipient, amount, memo, rail, fee comparison), presents one confirmation, and either executes on a real rail or hands the user a pre-staged action in the right app, then watches for the transaction to post and closes the loop with the receipt. "I can't send through Zelle directly, but I've staged it - here's exactly what to tap, and I'll confirm when it lands" is honest and still saves most of the work.Never claim a send happened without rail confirmation. Never hide that a capability is GATED. The registry status (doc 02) is what the voice layer reads.Rail selectionFor every send, the agent picks the rail by: recipient's reachable rails (do they have Venmo? is their bank on Zelle?), speed needed, fee, and the user's funding source. The comparison is shown in the confirmation: "Venmo instant: $0.88 fee, lands in minutes. ACH: free, lands Thursday." Fee-free-by-default: if the user did not specify urgency, quote the free rail first.Workflow: send money to someone1Parse: recipient (resolve from SOC-001 people directory), amount, memo, speed, funding source.2Fill gaps: missing recipient handle? Ask. Ambiguous person (two Marcuses)? Ask. New recipient? That is T5: full confirmation with recipient details read back, every time.3Select rail (above).4Confirm (T3/T5): one message with amount, recipient, rail, fee, funding account, timing. Exact restatement, no vague "send it?"5Execute via rail or handoff.6Verify: rail confirmation ID, or watch-for-posting with a deadline and a follow-up if it does not land.7Receipt: amount, recipient, rail, confirmation ID, when it lands, and the mitigation path if something is wrong.8Remember: update the people directory, the IOU balance if this settles one, and the outcome log.Workflow: paying people back (owed money)The IOU system (PAY-017/018/019): running balances per person, built from explicit IOUs ("I owe Sarah $85 for the Airbnb"), splits (below), and detected patterns (Sarah paid the dinner charge; the user sent nothing yet).Track: every IOU with source, amount, direction, date, status.Remind: the user asked to be reminded, or the other person asked the user through a shared channel the agent can see. Tone control (SOC-009): the user picks how the agent nags, from gentle to firm, and the agent never nags the other person without the user's explicit instruction (T3).Settle: one message, "settle up with Sarah? You owe her $85" leading into the send workflow with recipient, amount, and history pre-filled.Workflow: rentRent is the highest-stakes recurring send and gets its own flow:1Setup (T2): landlord details, amount, due date, method (portal, check, ACH, Zelle through the bank), late fee terms, grace period. Stored as a recurring commitment.2Each cycle (T4 once the user approves the standing instruction): confirm the amount matches the lease before paying; if the amount changed, stop and ask. Execute 2 business days before due date on the chosen rail, or stage the portal payment as a handoff with everything pre-filled.3Verify: confirmation number, or posting detection, with a same-day follow-up check. A failed rent payment is an urgent alert (doc 01 urgency rules), never a routine message.4Paper trail: every payment stored with confirmation, so a landlord dispute has receipts. Rent reporting enrollment (HOUS-003, GATED) offered once, not repeatedly.Workflow: billsDiscovery from BILL-001 recurring detection, due dates on the calendar (BILL-007), then per bill: autopay already on? Leave it, monitor it. No autopay? Offer to set it up (T3) or pay each cycle with confirmation (T3) or inside an envelope (T4). Every payment follows the same verify-and-receipt discipline as rent.Workflow: splits and requestsSplit (PAY-004): "split the $180 dinner with Alex, Priya, and Sam." The agent computes shares (equal, or itemized if the user gives them), creates IOUs, drafts requests, and on approval sends them on rails the recipients can actually receive. Requests are messages to people, so they are T3 with the exact text reviewed. Settle-up (PAY-019): when IOUs net out across a group ("Alex owes you $40, you owe Priya $40"), suggest the minimal set of transfers.Reversal contracts (the two-outcomes rule)From his earlier Ring agent work (Oct 8) the user stated: "2 outcomes book/cancel for everything we do." This spec proposes carrying that rule into Upmore money movement:ACH: reversible in narrow windows for specific errors; the agent states the real window at send time, not a fantasy recall button.Zelle/Venmo/Cash App P2P: effectively irreversible once received. The confirmation message says so in plain words before execution. This is why new recipients are T5.Wires: effectively irreversible. T5 always.Cards (disputes): the dispute flow with timelines and evidence checklist (CARD-010).Every send receipt includes: "wrong send? Reply 'wrong' and I'll start the mitigation path" with the actual mitigation for that rail (contact recipient, bank error claim, dispute where applicable).Fraud and velocity checksBefore any send: new recipient + large amount gets an extra verification question (SEC-012); velocity limits (per day, per week) from the user's envelope; scam-pattern phrases in memos or instructions ("IRS", "gift card", "urgent wire") trigger a hard stop with a plain explanation. These checks are in the compliance gate (doc 14) and cannot be disabled by prompt text.Build packet for Claude CodeContext: src/money/ with send.ts, rent.ts, bills.ts, splits.ts, iou.ts, rails/ (one adapter per rail: partner-ACH with a fake, handoff generator, receipt watcher), reversal.ts (per-rail contracts as data). Everything flows through doc 01's loop: gate, confirm, act, verify, remember.Constraints: no real money in tests. The fake rail must simulate confirmation, failure, and ambiguous timeout. Handoff flows produce exact tap-by-tap staging text. The voice layer cannot mark a send complete without a confirmation ID.Done when: pnpm vitest run src/money passes: full send lifecycle on the fake rail including idempotent retry after ambiguous timeout without double-sending; rent cycle pays early, catches a changed amount, and alerts on failure; split math correct across equal and itemized; reversal contract text present on every receipt; T5 new-recipient flow always asks. pnpm typecheck passes.How Claude Code proves it is betterBetter means fewer user actions and zero silent failures versus the apps. Test one (effort): script the 10 most common movement flows as conversations and count user messages versus Cash App and Venmo tap counts from the parity matrix (doc 03); movement flows must complete in 3 or fewer user messages for known recipients. Test two (safety): the adversarial suite - duplicate instruction ("send $50" twice in a row means once), ambiguous recipient, changed rent amount, rail timeout with actual success, scam-pattern memo. The system must behave correctly in every case, where the naive baseline (execute what the last message says) double-sends, misroutes, or lies about completion.Previous: Connector CatalogNext: Save EngineDraft specification.
