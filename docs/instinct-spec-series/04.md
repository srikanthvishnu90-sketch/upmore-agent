Upmore Spec 04: Connector Architecture"How would it know the connectors design - how you connect something." This doc is the general answer: one connector model that every source plugs into, whether it is a bank behind an aggregator, a brokerage with OAuth, a utility with only a web login, or a CSV the user drops in chat. Doc 05 then enumerates every connector to build.GoalBuild src/connectors/: a framework where adding a new financial source means writing one adapter against a fixed interface, and where every connection behaves identically to the user: connect, see status, get data, fix when broken, revoke cleanly.The connector modelA connector is a record plus an adapter:ConnectorRecord {
id: conn_01H...
provider: "chase" | "plaid:wells" | "schwab" | ...
authMethod: AGGREGATOR | OAUTH | VAULTED_CREDENTIALS | MANUAL
scopes: [READ_BALANCES, READ_TRANSACTIONS, INITIATE_TRANSFER, ...]
consent: ConsentRecord        // what the user agreed to, when, verbatim
status: HEALTHY | STALE | NEEDS_REAUTH | BROKEN | REVOKED
lastSyncAt, lastSuccessAt
capabilities: [ACCT-001, TXN-001, ...]   // registry IDs it powers
}The adapter interface, five verbs:connect(user, credentials) -> ConnectionSession   // may hand off to OAuth or aggregator UI
sync(conn, since) -> SyncBatch                    // accounts, transactions, holdings, bills
act(conn, action, params) -> ActionResult         // only for write-capable connectors
health(conn) -> HealthReport                      // latency, error, reauth needed
revoke(conn) -> void                              // token destruction + data retention noteThe agent never talks provider APIs directly. It talks the five verbs. That is what makes 50 connectors maintainable: the loop (doc 01) knows one interface.Auth methods, in order of preference1Aggregator (Plaid, MX, or Finicity): one OAuth-style hosted flow covers thousands of banks and cards with tokenized access, no stored passwords. This is the default for bank, card, loan, and investment read data. Cost and coverage decide the vendor; design the adapter so the aggregator is swappable behind the interface.2Direct OAuth: where a provider has real OAuth (brokerages, payroll platforms, some utilities), connect directly for richer scopes or better rate limits. Tokens live in the vault, refresh handled centrally.3Vaulted credentials: for sources with no API and no aggregator coverage (many utilities, insurers, landlords' portals). The user stores credentials in the vault; the connector logs in through a controlled browser, scrapes narrowly, and degrades gracefully when the page changes. Clearly labeled in status as the least reliable class.4Manual: CSV import, PDF statement parsing, receipt forwarding, photo entry. Always available as the floor. A manual connector for cash spending is a first-class connector, not a hack.Read versus write: aggregator and OAuth connections start read-only. Write scopes (initiate transfer, place order) are separate consent grants with their own screens, and they map to autonomy tiers T3 and up (doc 01).Consent recordsEvery connection stores what the user agreed to in plain words: the scopes, the data retention rule, and the revocation path, with a timestamp. Consent is a first-class record because (a) the compliance layer (doc 14) needs it for audits, (b) the agent must be able to answer "what are you connected to and what can it do" from data, and (c) revocation must actually revoke: destroy tokens, stop syncs, and report what data is retained and why.The sync enginePolling cadence per connector class: banking transactions at least daily plus webhook-triggered when the aggregator supports it; balances on read demand with caching; bills monthly; holdings intraday during market hours for alert purposes.Webhooks first: aggregator webhooks (transactions available, item needs reauth) drive the loop's OBSERVING state. Polling is the fallback, not the primary.Normalization: every sync batch lands in one canonical schema: Account, Transaction, Holding, Bill, Person. Merchant normalization (TXN-004) runs at ingest so every downstream capability sees clean names.Source-of-truth ranking: for any datum, one connector class wins. Balances: aggregator or direct OAuth beats scrape. Transactions: aggregator beats email receipt parsing. The ranking table lives in config, and conflicts are reported per doc 01's error rules, never silently merged.Freshness: every datum carries lastSuccessAt. The voice layer (doc 11) must be able to say "as of an hour ago" because the sync engine stamps it.Health, repair, reauthConnections break constantly in consumer finance: passwords change, MFA resets, aggregators deprecate endpoints. The framework treats this as normal:health() runs on a schedule and after any sync error. Status NEEDS_REAUTH produces exactly one calm user message with a one-tap relink; repeated breakage on the same connector escalates the message but never spams (proactivity budget, doc 01).BROKEN connectors degrade capabilities honestly: the registry flips dependent capabilities from VERIFIED to their degraded status and the agent stops citing fresh data from them.Connector breakage is itself a sync input: "Chase needs you to sign in again" is a first-class event, not a log line.Security postureCredentials and tokens in a dedicated vault, encrypted at rest, never in the database with financial data, never in logs. The adapter receives a handle, not the secret.Least privilege: request the minimum scopes per connector; write scopes only when a write capability is built and the user granted it.Every act() call passes through the autonomy gate (doc 01) and the compliance gate (doc 14) before reaching the provider.Full audit log: every sync and action with timestamps, params (secrets redacted), and results. This log powers the user's "what have you done" answer (SEC-009).Build packet for Claude CodeContext: create src/connectors/ with the five-verb interface, the ConnectorRecord store, the consent store, the sync engine with a scheduler, the normalization pipeline, and three reference adapters: (1) a fake aggregator adapter with a fixture bank for tests, (2) a manual CSV adapter, (3) a stub OAuth adapter for one sandbox provider.Constraints: no real provider credentials in tests; all adapters tested against fixtures. The autonomy gate and compliance gate are called in act() before any provider call; prove it with a test that a T5 action never reaches the adapter.Done when: pnpm vitest run src/connectors passes: connect/sync/act/health/revoke lifecycle for the fake adapter, reauth flow flips status and emits exactly one user event, sync conflict resolution follows the source ranking, revoke destroys tokens and writes the retention note. pnpm typecheck passes.How Claude Code proves it is betterThe framework is better when adding a new connector is provably cheap and failures are provably contained. Test one: have a fresh agent session add a brand-new fake provider using only this doc and the interface. It passes if the new adapter compiles, registers, syncs, and appears in the capability status output with zero changes outside src/connectors/adapters/newprovider/. Test two: the failure suite - kill the fake provider mid-sync, expire its token, corrupt one batch. The system must surface NEEDS_REAUTH, keep serving last-good data with age labels, and log everything. Baseline: a design where each provider is called ad hoc from capability code; count the files touched to add a provider there versus here.Previous: Parity SpecNext: Connector CatalogDraft specification.
