## Why — two layers

### Layer 1 (trigger): no layer maps the fact to the board's option vocabulary

150 classifies the field `standard` / `education_discipline`
(packages/domain/150-career-portal-browser.js, classifyKind's
discipline rule), so 149 fills it with the profile's free-text
discipline fact. The board's control is a fixed-option "closest
response" widget; the helper's option matcher
(scripts/career/portal-browser-helper.cjs, `matchOption`, and the
`option_not_found` returns in its fill paths) finds no option for a
free-text degree string and the fill is refused.

The board's actual option list for this field appears in **no**
record (not the diag result, not the inventory scan, not any repo
fixture — verified by search this session), so a closest-option
picker cannot be built or verified from fixtures without inventing
the vocabulary. The addendum's own root cause assigns that derivation
to the ask/mapping path (module 172): derive the closest option from
the confirmed fact **with user confirmation, never by invention**.
That half of F-023 stays open after this lane (see "What this fix
does not do").

### Layer 2 (the silent loss — this lane's fix): 149 discards the board's fill verdict

Module 150's fill contract already reports refusal precisely:

- packages/domain/150-career-portal-browser.js:516 `fill(fieldId, value)`
  returns the value on success and `undefined` on refusal, recording
  `state.fillFailures.push({ field_id, reason, wanted })` (e.g.
  `option_not_found`); over the worker bridge
  (supabase/functions/_shared/career_task_bridge.js, `fill` returns
  the worker result verbatim) the same refusal arrives as `null` —
  exactly the `result: null` in the live record.
- 150's own comment (line ~548) states the contract's second half:
  "the field stays unset — **149 then asks the user about it if it is
  required**."

That second half was never implemented. In
packages/domain/149-career-portal-apply.js, `prepareRound`'s fill
loop calls `board.fill(...)` and **unconditionally** records success
at every fill site — lines 823 (saved answer), 834 (standard/profile),
839 (screening), 850 (free_text), 856 (eeo), 862 (attestation):

```js
board.fill(f.field_id, value); filled[f.field_id] = { value, source: "profile" };
```

The return value is never read, and `board.fillFailures` is never
read anywhere in 149 or 155 (grep: zero hits). Both downstream guards
then skip the field by construction:

- the observation gate (line ~887): `if (observed[id] === undefined)
  continue;` — a refused fill reads back absent, so no mismatch is
  ever raised for it;
- the required-ask sweep (line ~922): an `answer_not_observed` ask is
  pushed only when the field is **not** in `filled` — and the loop
  just put it there.

So a required field the board refused is carried as answered through
the whole prepare: the stepLog affirmatively records a `fill` step
for a fill that never landed, and the gap surfaces only at the
doorstep, misdiagnosed as a persistence failure (D13
INCOMPLETE_PAYLOAD — "the fills did not persist" — when in fact the
fill never landed at all), or not at all when other asks end the run
first (the witnessed diag run ended `awaiting_user` on other fields;
the major field was not among the asks). This contradicts the
addendum's Expected: "the confirmed fact is mapped to the board's
closest fixed response, **or the run surfaces a named ask — never a
silent unfilled required field**."

## The fix (149 only, general)

Route every `prepareRound` fill through one verdict seam
(`attemptFill`): a fill counts only when `board.fill` returns a
non-null, non-undefined value (the contract on every board: sandbox
returns the value, 150 returns the value / `undefined`, the worker
bridge returns the value / `null`). On refusal:

- `filled[field_id]` is **not** recorded;
- a `fill_refused` step is logged with the field, the source metadata
  the fill step would have carried, and the board's recorded failure
  reason when the board exposes it (`board.fillFailures`, e.g.
  `option_not_found` — otherwise `fill_returned_no_value`);
- a named ask `{ field_id, reason: "fill_refused" }` is pushed, so a
  required field gates the run as `awaiting_user` with the ask
  visible (the existing required-ask logic does the gating), and an
  optional field's refusal is recorded without blocking the run.

Throwing fills (unknown field, resume sha mismatch) keep their
existing behavior — only the returned verdict is newly honored. The
doorstep repair loop and `submitDoorstep` are untouched (submit path
is out of this lane's scope).

This is a general capability: it works for any field, any board, and
any refusal reason — the FDSE major field is the witness, not the
scope. It invents nothing: no value is derived, mapped, or guessed;
the user is asked, which is the record's sanctioned fallback.

## What this fix does not do

- It does **not** derive the closest option from the discipline fact.
  That mapping (module 172's ask path, with user confirmation) needs
  the board's option vocabulary captured from a live form — no live
  drives are in this lane's scope, and no record carries the list.
  F-023 therefore closes only in its silent-loss half here; the
  mapping half stays OPEN and must not be read as fixed by this lane.
- No change to the helper's option matcher, to 150, or to any flag /
  submit-path code.

## Enforcement (BUG LAW)

The permanent guard is the fail-first test
`tests/career-fill-refusal.test.cjs`: a board implementing 150's
documented fill contract (value on success, no-value + fillFailures
on refusal) drives 149 through the FDSE-shaped case — a required
closest-response field whose confirmed fact matches no option must
end `awaiting_user` with a named `fill_refused` ask and a
`fill_refused` step, never a claimed fill; an exact-option value
still prepares; an optional field's refusal is recorded without
blocking. Red on the base tree, green with this fix; it stays in the
suite so the discarded-verdict seam cannot silently return.
