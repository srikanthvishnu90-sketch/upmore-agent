   the fill half is below).
3. The helper (scripts/career/portal-browser-helper.cjs) fills a native select in

   matchOption (line 304) tries exact, head-segment, then — only when the wanted value
   is itself decline-class — a decline-class branch (lines 312–315) keyed on
   `isDeclineText` (line 303):
   `/decline|prefer not|do not wish|don t wish|dont wish|not (to )?answer|not (to )?disclose|no answer/`

## Why the disability select misses and the veteran select hits

Lever's captured question bank (evals/apply/questions-ci-b.json — `eeo[disability]`,
type "select", identical across every captured posting) renders exactly three options:

- "Yes, I have a disability, or have had one in the past"
- "No, I do not have a disability and have not had one in the past"
- "I do not want to answer"  ← the refusal option (the OFCCP CC-305 wording)

Normalized, the refusal reads "i do not want to answer". The decline predicate covers
the WISH family ("do not wish", "don t wish", "dont wish") and "not (to )?answer" —
which needs "not answer" / "not to answer" CONTIGUOUS; this text has "not WANT to
answer". It has no "decline", no "prefer not", no "no answer". So no option is
decline-class, the prefix fallback cannot fire either, and matchOption returns null →
`{filled:false, reason:"option_not_found"}` in ~150 ms → field unset.

The veteran select renders its refusal as "I decline to self-identify for protected
veteran status" — contains "decline" → the decline branch hits. That single-word
asymmetry is the whole defect: ONE semantic choice (refuse to self-identify) worded
with WANT on the disability form and DECLINE/WISH on its siblings, and the fill-side
vocabulary only knew the latter.

Reproduction (this session, the helper's matcher code run verbatim against the
captured option sets): disability set + "Decline to self-identify" → **null**;
veteran set + same value → the decline option. Neither substantive disability
option is decline-class under the current predicate (checked) — so widening the
vocabulary cannot mis-select a substantive answer.

The same predicate copy lives in the widget drive's in-page matcher
(portal-browser-helper.cjs:510, `isDecline`, used at :519 — decline branch gated on
`wantedDecline` at :511). A widget-rendered EEO question with the WANT wording would
miss identically; both copies carry the same vocabulary and are fixed together.

## Why the earlier decline-vocab fix did not cover this

DECLINE-VOCAB (04e24fde, host merge 485a432b) aligned the GATE side: 149's
EEO_DECLINE_MEANING accepts the board's rendered refusal at the observation compare.
That never fires for this field — the fill never lands, so there is no rendered value
to accept (optional + absent-from-observed ⇒ the gate skips it). FILL side ≠ GATE
side; this note is the fill side, as the F-024 ledger entry pinned it.

## Fix shape (general; no company literals, no fixture ids in product paths)

Extend the decline-class vocabulary in BOTH predicate copies (helper :303 and the
widget matcher :510) with the WANT refusal forms, in the same alternation shape:
`do not (wish|want)`, `don t (wish|want)`, `dont (wish|want)`. Nothing else changes:

- The predicate still fires ONLY when the wanted value is itself decline-class
  (matchOption :312 gate; widget :511 gate), so a substantive requested answer can
  never be routed to a refusal option by this branch.
- Exact / head-segment matching still runs first; a user's explicit EEO choice that
  names an option verbatim is untouched.
- The substantive Yes/No disability options stay non-decline under the widened
  predicate (guard asserts this), so the first-decline-hit can only be the refusal.

Test seam: export `matchOption` and `isDeclineText` from the helper (same pattern as
the existing `detectChallenge` / `captchaTech` exports) so the guard drives the real
matcher, not a copy.
