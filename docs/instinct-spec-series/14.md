The gate consults the regulated map as data: capability -> requirement -> partner status -> allowed or blocked with the reason string the voice layer speaks.Constraints: the gate is one call site in the loop, not per-capability honor system. A capability with a requirement and no live partner is blocked in code, and the block message is specific.Done when: pnpm vitest run src/compliance passes: every regulated capability in the map resolves to a requirement; blocked capabilities produce the specific user message; disclosures fire contextually once; incident playbooks execute their step lists against fixtures. A seeded attempt to execute a GATED rail fails closed.How Claude Code proves it is betterThe eval is negative space: scan the whole product surface (every compose-able message template, every onboarding screen, every store listing draft) for capability claims, then diff against the registry VERIFIED set. Zero unmatched claims required. Second: the regulated-map completeness check - run the full 316-capability registry through the map; every capability must resolve to "unregulated" or a named requirement with a partner state.
