**Mechanism (evidence-backed):** the succeeding capture emits a KEYED fact — `{kind: "recruiter_contact", key: "northwind ledger", value: "Dana", evidence: "recruiter contact at Northwind Ledger is Dana", at: …}` (module 142's `recordKeyedFact`). `career_host.js`'s account write-back (`extractSnapshot`) placed the turn's whole stated-facts working set into the account patch's `stated_facts.facts`. The deployed validator — migration `20261016120000_career_account_stated_facts.sql`, the only definition of `career_host_commit` — accepts into `facts[]` only 9 kinds (`year, majors, geography, target_firm, level, excluded_level, school, experience, tone`) with bounded scalars, ≤40 facts, ≤32 KB; a `recruiter_contact` element raises `invalid stated facts`. The commit is atomic, so the raise rolled back the message pair, the snapshot, and the receipt with it; the persistence layer maps any RPC error to `storage_unavailable`; the handler mapped that to the bare 503. The deploy lane's key suspect — a legacy shape in the stored record — is DISPROVEN as the cause: the test account's live `career:account` record (read read-only) is clean (5 facts, all whitelisted kinds, offer null, 792 bytes). The failing write was the NEW patch, not the stored record. No lab world could see it: the node harness never runs the SQL validator, and fix lane 1's persistence fake neither validated the patch nor applied it to its fixture account.

**Reproduction (before the fix):** staged REAL handler (the deployed tree, remote services faked) + a commit wrapper enforcing the migration's validator transcription, seeded with the account's ACTUAL stored record → the turn emitted exactly the patch above (`facts[5]` = the recruiter_contact fact), the validator raised, the handler returned 503 with the live body byte-for-byte, zero messages stored; the recall ask then routed `company_intel`. The migration's element predicate was also evaluated in real Postgres against both patch shapes (read-only SELECT): old patch `facts[]` = **1 violating element**; fixed patch `facts[]` = **0**.

**Fix (`supabase/functions/_shared/career_host.js`, the account boundary only):** the write-back splits the record by the validator's own acceptance rule (`statedFactsRecordForCommit` / `sqlStatedFactOk` / `STATED_FACT_SQL_KINDS`): SQL-shaped facts ride `facts[]` (≤40); every other fact rides the sibling **`keyed`** array inside `stated_facts` — the validator inspects only `facts` elements + offer, and the commit merge (`account := account || patch`) stores the sibling verbatim. The `createTurnCtx` seed folds `facts` + `keyed` back into the one working set, so 142's record is unchanged in content — only its carriage differs; no fact is dropped or altered. The merge identifies keyed facts by kind+key (a corrected name at one company replaces; two same-named contacts at different companies both stand). Change detection compares working sets (facts+keyed), so an unchanged record never churns the account row; a legacy record still holding keyed kinds inside `facts[]` heals into the split shape on its first changing turn (guard-pinned). A defensive evidence-shed keeps a pathological record under the validator's 32 KB cap without touching kinds, keys, or values.
