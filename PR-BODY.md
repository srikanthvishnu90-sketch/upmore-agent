# F3: Onboarding under 2 minutes — name, resume, target roles, first reviewed match

A new person finishes onboarding in one session on four screens: name → resume (upload or paste) → target roles → the first reviewed match. The flow (`src/career-onboarding.js`, `TraineeOnboarding`) runs over the product's real models, not a parallel vocabulary: the profile is the 122 master profile, the resume lands through 122's typed ingest (drafts stay drafts, failures are typed with a next step), target roles land in `preferences.roles` and the goal rides the 142 goal-spine carriage (`stated_facts` `{kind:"goal", key:"career"}`), and the first match is composed by 121's own matcher (`profileFromPersona` + `scoreFit`) over the real `career_postings` shelf. Every answer is stored as a confirmed 122 fact carrying provenance `owner stated (web onboarding, <date>)` and a confirmation event id — the shape the prepare contract consumes — so nothing asked here is ever re-asked. The step a returning person lands on is derived from what is stored, so leaving mid-flow resumes at the first unanswered step with earlier answers intact.

## The five checks

- **(a) Under 2 minutes, one session, measured.** The budget lives in one place (`Flow.BUDGET_MS = 120000`, dated comment). `tests/career-onboarding-web-dom.test.cjs` drives the whole flow through the real component under jsdom with a synthetic TEST person — type name, paste resume, enter roles + goal, land on the match — and asserts exactly the four screens in order and wall time under the budget: **measured 48–147ms wall across runs** (printed by the test; the jsdom drive is not a human, so the honest claim is the interaction shape: 4 screens, one input action per screen, no sub-wizards — the budget constant is what a human run is judged against).
- **(b) No dead ends; every input validated against the real models.** Name → `basics.name` + confirmed fact; an empty name is a typed refusal and the step does not move. Resume → 122 `ingestResume`: a `.pdf` upload returns `reason_class: "unsupported"` with 122's own next step ("…or paste the resume text instead"), an empty paste returns `"empty"` — both surface in place (`role="alert"`) with nothing stored and the step unmoved; a good resume produces draft facts (never canonised), the 122 ingest audit entry, and the `resume_sources` active record. Roles/goal → `preferences.roles` / `preferences.goals` + the stated-facts goal record; a test derives the matcher's families through 121's own adapter (`profileFromPersona` → `role_families: ["Data/ML"]`) from what the flow stored.
- **(c) Every question stored as a reusable answer.** Each answer is a confirmed 122 fact with `provenance: "owner stated (web onboarding, 2026-10-22)"` and its own `confirmation_event_id`; the name also lands in the WO-102 answers record (`profile.answers.full_name`). Proof with the product's own prepare contract: `trustedManifest` (real `extension/lib/trainee-core.js`, loaded by vm like the repo's fact-import tests) over the stored profile keeps `full_name` in the manifest, and no onboarding store is excluded for provenance or confirmation. A completed profile starts a fresh session at `done` — nothing is re-asked.
- **(d) Skippable and resumable.** The current step is derived from stored state plus explicit skip records (`{at, reason: "skipped by the person"}`). Tests: answer name + resume, JSON round-trip the profile (the host's persistence shape), remount — the flow resumes at `roles` with answers intact and coverage reading `2/3`, unreduced. Skipping the resume moves on with the reason kept, and the match screen names it in its basis.
- **(e) The first match is real-shaped, composed by the matcher.** `firstMatch` scores every pool posting with 121 `scoreFit` (ask families derived from the stored roles): considered = kept + dropped exactly (3 = 2 + 1 in the test pool), the top kept posting is the match with `scoreFit`'s own reasons (e.g. `role family Data/ML is one you asked for`) — no hardcoded sample — and the out-of-family posting returns dropped with the role-family rule that dropped it. Empty pool: `match: null`, fraction `0/0`, honest no-match copy. The match card exposes the marked F2 slot (`data-f3-card-slot`, with the job id) where the approval card mounts for the prepared application.

## Wiring and integration points

- The app gains a "Start" button in the chat header and a `#careerOnboard` screen; `renderCareerOnboarding` hosts the component: profile persisted per signed-in user in device local storage, posting pool read from `career_postings` (authenticated read, open postings, newest 200, `description` → `jd_text`). `src/build-app.py` inlines `career-onboarding.js` + CSS and the real 122/121 modules (verbatim — a check in the lane's evidence confirms byte-identical inclusion).
- **Integration point, stated plainly:** syncing the web profile into the agent-chat account record (the `career_host` stated-facts carriage the chat goal frame reads) is host wiring not in this PR — until it lands, the device-stored profile is the copy the web flow reads, and chat does not see web onboarding answers (and vice versa). The stores are shape-identical (122 profile + stated_facts goal record), so the sync is a transport, not a remodel.
- The F2 approval card mounts into the match card's `data-f3-card-slot`; nothing is prepared or submittable from this flow.
