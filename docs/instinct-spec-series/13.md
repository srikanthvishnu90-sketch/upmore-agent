Upmore Spec 13: Testing and Betterment - Proving It Is Better"How do we test it's better." Not "does it work" - that is table stakes from each doc's acceptance tests. This doc is the standing harness that answers the harder question: is Upmore better than the alternatives, and is it getting better over time.GoalBuild evals/: the harness that runs acceptance tests per capability, benchmarks against named baselines, judges response quality, red-teams the safety boundaries, and gates every change on the whole suite. The implement-test-improve loop the user has used in earlier prompts becomes infrastructure here.Layer 1: Capability acceptance testsEvery registry capability (doc 02) has evals/capabilities/<ID>.test.ts: fixture inputs, the expected behavior, and a pass/fail assertion. TESTED status requires this test green; VERIFIED requires it green against a sandbox or live adapter. The registry refuses a status the tests do not back (doc 02 enforcement).Layer 2: Scenario suiteEnd-to-end multi-turn scenarios through the operating model (doc 01): 25 adversarial scenarios from the operating model doc, 12 gold voice conversations from doc 11, 10 money-movement safety scenarios from doc 06. These run the assembled system, not units. Every release must pass 100 percent. New failure found in production: it becomes a scenario before the fix ships.Layer 3: Benchmarks against named baselinesThe "better" bar, per surface:Assistant quality: vs a generic frontier chatbot given the same fixture data, on the 30-scenario blind pairwise eval (doc 11). Target: win 70 percent of pairs, zero grounding losses.Subscription and savings finding: vs Rocket Money and Monarch-style detectors on the 40 financial lives (doc 07). Target: recall at or above both, with verified-dollar accounting neither does.Assistant answers inside banking: vs Eno/Erica/Fargo-style bank assistants on 25 cross-bank questions. The baselines see one institution; Upmore sees the whole picture. Score on correctness, completeness, and honesty about unknowns.Earn apps: vs Propel/Freecash on requirement tracking and effective-rate honesty (doc 08).News relevance: vs raw feeds and a generic finance app's notifications on precision/recall (doc 10).Each benchmark is scripted, fixture-based, and re-runnable. Baseline outputs are captured and versioned so "better" is measured, not asserted.Layer 4: Judged quality evalsLLM-judge with fixed rubrics for voice (doc 11 rubric), usefulness, and honesty, calibrated against human judgments on a 20 percent sample. Judge models change; the rubric and the human calibration set are the constants. Every rubric has named failure classes (filler, overclaim, hedge-stack, wrong severity) so regressions are diagnosable.Layer 5: Safety and boundary evalsAdvice guard: 40 + 20 held-out adversarial prompts (doc 09), 100 percent hold required.Prompt injection through data: the doc 12 adversarial set, 100 percent required.Money safety: the crash, duplicate, timeout, and scam-pattern scenarios from doc 06, 100 percent required.These are hard gates: a single failure blocks release regardless of every other metric.The loopPer build session, the contract with Claude Code or Codex: implement the packet, run its acceptance tests, run the capability's eval section, then run the affected benchmark. Improve until green, then show the evidence (test output, eval scores) - per the verification-first practice from doc 00. Weekly: full suite plus fresh baseline captures. Monthly: ablation re-runs (doc 12) and a parity sweep (doc 03).Metrics that matterTask success rate on scenarios (by domain).Grounding error rate: money statements without correct source and as-of. Target zero.Autonomy accuracy: actions taken at the right tier; over-asking and under-asking both counted.Time-to-outcome per flow vs app tap counts (doc 03 conversion test).User corrections per 100 actions, trended down.Proactive precision: fraction of proactive messages the user acted on or rated useful.Build packet for Claude CodeContext: evals/ with runner.ts (executes suites, stores results versioned), judges/ (rubric configs and calibration sets), baselines/ (captured baseline outputs), gates/ (release gate config). pnpm eval runs the fast suite; pnpm eval:full runs everything including benchmarks.Constraints: evals are fixture-based and deterministic where possible; judged evals record model and rubric versions; safety gates cannot be skipped by a flag in CI.Done when: pnpm eval runs green on the as-built system, produces a results table per layer, and demonstrably gates: a seeded regression (a deliberately broken capability) fails the run and names the failing layer.How Claude Code proves the harness itself is betterA harness that cannot catch a planted bug is decoration. Mutation testing: seed 10 known defects (skip verification, swap tier check, drop freshness label, overclaim a capability, break split rounding) one at a time. The harness must catch all 10 and name the right layer for each. Any missed mutation gets its own new test before the harness is trusted.Previous: Training DataNext: Compliance GatingDraft specification. Nothing here is financial advice; nothing moves money.
