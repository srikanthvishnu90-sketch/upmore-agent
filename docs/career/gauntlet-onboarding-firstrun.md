Build: HEAD 6fef2f2 (worktree career/gauntlet-onboarding) · Trials: 3 per case, clean state per trial · Harness: pilot-lib chat path (120 → 130 → 142 → 141, wrapped by 143), evidence Tier B (staging harness) · Generated by scripts/career/gauntlet/onboarding-firstrun.cjs from the OB-SUMMARY trial records — not hand-typed.

Verdict vocabulary (quality-spec 00): PASS / FAIL / NOT IMPLEMENTED (abbreviated NI below) / BLOCKED. A case verdict is the worst of its 3 trials; PASS requires all 3 trials to pass. FAIL = implementation present but wrong; NI = implementation absent; BLOCKED = the harness cannot represent the precondition/shape (seam named).

Grading note — the containment fallback: most first-contact turns on this build are answered only by 143's containment fallback, whose text is 140's `unmatched` fallback ("I didn't catch that…"). Quality-spec 00 says that reply is never an acceptable NOT IMPLEMENTED reply (H-1, S1). This set grades the Part 2 *capability* per the lane brief — absent capability = NI — and records the fallback text verbatim in every affected case so the H-1 defect is visible, not hidden. OB-08 is the exception that proves the distinction: there a real handler (142-career-router) claimed the email-task turn and itself returned the dead-end text, which is present-but-wrong = FAIL (S1), exactly as 00/H-1 prescribe. If the owner prefers the strict-00 reading throughout, every NI below whose only reply is the containment fallback converts to FAIL (S1, H-1) — the per-case records carry everything needed to re-derive that.

## Harness seams hit

- **S-BUBBLE:** pilot-lib/143/140 flatten product bubbles: chatTurn delivers a single reply string; 143 extractReplyText joins bubbles[] with ' '; 140 composeText groups up to 3 sentences per recorded bubble. Delivered-bubble counts are harness counts; raw reply lines are recorded alongside.
- **S-PROFILE:** No 'no profile exists' representation: 130.handleChat requires ctx.profile. No-profile is ctx.profile=null + ctx.profileExists=false + ctx.firstName/agentName, none of which any current handler reads.
- **S-PERSIST:** No cross-session lifetime store in the harness: lifetime = same session/profile objects reused; new session = fresh H.session with the same profile object.

- S-PROFILE bit on OB-01/02/03 (no handler reads profileExists/firstName, so the trigger cannot fire), OB-04/05/09 (empty-profile substitution for store inspection, recorded in each case's case-setup tool record), and OB-08.
- S-BUBBLE bit on every exact-bubble assertion: it is the reason raw reply lines are recorded next to delivered bubbles in every record; on this build it did not change any verdict, because no handler produced the greeting text in any form (raw or delivered). If a future build returns the two greetings as one reply string, OB-01/02/03 will grade BLOCKED (seam) — not FAIL — until the harness can deliver multi-bubble results.
- S-PERSIST bit on OB-01 (same-lifetime = same session object) and OB-06 (new session = fresh H.session, same profile).

## What Codex's Part 2 implementation must provide for this set to pass

1. A first-contact trigger keyed on 'no profile exists' that fires exactly once per user, reading a known first name from host identity (never contacts) and emitting the two exact Part 2 bubbles as separate bubbles — which also requires a multi-bubble result shape the harness can deliver (S-BUBBLE).
2. The retained-request acknowledgment + a retained-request store that re-surfaces after confirmation (OB-03).
3. Intro-fact extraction with an explicit unconfirmed state in the store, a 2–4 line playback ending 'Did I get that right?', a confirmation gate enforced at every artifact route (OB-04 S0), correction overwrite with re-confirmation (OB-05), one-at-a-time missing-fact questions with defaults (OB-09).
4. Just-in-time Gmail/Calendar connection surfacing from a task that needs it, and never during onboarding (OB-08).
