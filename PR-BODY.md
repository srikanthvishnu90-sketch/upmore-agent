# F2: The approval card (BUILDER-PLAN-48H, item F2)

The approval card is now a review surface, not a summary: one card model in module 175 shows, per application, the job, the company, the match reason and **every field answer that will be sent**, each answer carrying its verification state, and the reviewer can approve, edit or reject **per application** and batch-approve the reviewed set — on the web and in the channel card, rendered from the same model. The work starts by porting the Lane B card stack (modules 167/170/172/173/175 @ `5ffab100`) onto trunk, whose guards pass here (34/34, one documented reconciliation), and the commit still runs the existing approval machinery exactly as before — 155's own mint, via 175's tap — with 'Submit when complete' present on the card but built disabled and wired to nothing.

## The five checks

- **(a) Job, company, match reason, every field answer** — `tests/career-approval-card-f2.test.cjs`: every field of every application is asserted present (label + value) in **both** renderers, from all three real input shapes (canonical; trunk v1 message-card entry; trunk v2 cloud item). Verification is derived from evidence in the payload — v1: the provenance ledger's confirmation event naming the answer's own factId; v2: the prepared field's `confirmation_event_id`; absent evidence = unverified, never assumed. A missing match reason renders as "not recorded" — never invented. Blank fields are named, not dropped. Coverage is reported covered/total (fixture: answers verified 9/12).
- **(b) Approve / edit / reject per application + batch approve** — approve and reject are per application; rejection without a reason is refused (`REJECT_REASON_REQUIRED`) and the reason is recorded on the card and in the commit set. Edit changes the value the commit set will send, re-marks the field **EDITED** (it no longer counts as verified; the original stays on the record) and returns the application to review. `reviewCommitSet` partitions every application exactly once — approved with its exact fields / dropped with its reason / held back with the rule that holds it. `tapReviewCommit` runs the existing tap (155's mint) **only** when the reviewed set is the whole card; a changed or unfinished set refuses `COMMIT_SET_INCOMPLETE` with the partition attached and the run untouched (the mint binds the exact payload; a changed set needs a fresh prepared card — 173's supersession doctrine — never a silent subset approval). Both directions are proven against a live 155 run.
- **(c) Unverified is visually loud** — web: the field row gets a 4px danger bar, a tinted background, a bold value and a `⚠ UNVERIFIED` / `⚠ EDITED` / `⚠ CHECK` chip (asserted in the browser by class **and computed style**); channel text: the line itself is prefixed `⚠`. Verified answers render plainly (asserted).
- **(d) One model, two renderers** — `renderReviewHtml` (+ `wireReviewCard` DOM wiring) and `renderReviewText` (the channel card: the WO-022 numbered format the bridge already emits, with its reply footer). `reviewChannelActions` returns the bridge's button binding `{action:"approve", version, eventId, runId, cardSha256}` — no payload, no authority in the button.
- **(e) Browser test green** — `tests/career-approval-card-f2-browser.test.cjs` (Playwright): assembles the real surface (module 175 + `src/trainee-design-tokens.css` + `src/career-approval-review.css`) and drives render → per-app approve → per-field edit → per-app reject with reason → batch approve → commit (asserting the exact partition the host seam receives) → submit-when-complete inertness under a forced click. **4/4.** Posture is printed by the run: sandboxed Chromium by default; on this VM the operator opt-out posture (`UPMORE_CHROMIUM_SANDBOX=off`) because this host class cannot initialize a sandboxed Chromium for any user (proven in `docs/e2e/H4-DRIVER-ERROR-ROOT-CAUSE.md`).

## Design

`src/trainee-design-tokens.css` is the one token file: graphite `#1E1F24` + silver base, `--accent-plum: #6B4F7E` as the **one** plum token (light plum `--plum-light: #A58FB8`), serif headers / Inter body — if the owner picks `#4A2F5E`, the change is that one line. Plum appears only on the primary/active affordances; the unverified treatment uses the separate semantic danger tokens. No connectors page, no mockups — the component renders real model data only; TEST data is labeled by the card's `world` line.
