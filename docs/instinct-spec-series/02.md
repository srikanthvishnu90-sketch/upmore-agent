Upmore Spec 02: The 100 Percent Capability InventoryThe user asked: "how do we make it so that we know 100 percent all the capabilities it can do." This doc is the answer: a registry where every capability has an ID, a status, and an owner doc, plus the standing process that keeps the inventory complete so nothing is ever unknown.GoalBuild src/capabilities/registry.ts as the single source of truth for what Upmore can do. If it is not in the registry, the agent does not claim it. If it is in the registry, it has a status that is honest.Registry schemaEvery capability entry:id: ACCT-001            (domain prefix + number, stable forever)
name: read balance
domain: accounts
status: CLAIMED | BUILT | TESTED | VERIFIED | GATED | NOT_WIRED
tier: T0                (autonomy tier from doc 01)
ownerDoc: 05            (which spec owns the detail)
connectors: [plaid]     (what it needs live)
description: one line
testRef: evals/capabilities/ACCT-001.test.tsStatus meanings, enforced in code: CLAIMED is registered but unbuilt (the agent must say "not yet" if asked); BUILT is implemented; TESTED passes its acceptance test; VERIFIED passed against a live sandbox or real account; GATED means blocked on a partner or license and the agent says exactly that; NOT_WIRED means the rail exists but is not connected yet. CORE-016 version and changelog awareness (T0).Keeping the inventory at 100 percentThe registry is complete only if a process keeps it complete:1Parity sweep: doc 03's per-app checklists regenerate quarterly from the apps' current release notes and store maps; any app feature without a registry ID gets one with status CLAIMED.2Request mining: every user request the agent cannot fulfill creates or updates a registry entry, so the catalog grows from real demand.3Connector diff: when a connector adds an API surface (doc 04 tracks per-connector surfaces), the registry review asks what new capabilities it unlocks.4Weekly digest: the registry diff (added, status changes) is a standing report, so "what can it do" is always answerable from code, not memory.Build packet for Claude CodeContext: src/capabilities/registry.ts plus one stub module per domain. The registry is typed, validated at boot (unique IDs, valid tiers, existing test refs), and queryable. Voice layer reads it; nothing else hardcodes capability claims.Constraints: no capability may be added without a status and a testRef. Status VERIFIED requires a linked passing test artifact.Done when: pnpm vitest run src/capabilities validates the registry schema, all 316 IDs load, and a CLI (pnpm capabilities --status) prints the inventory by domain and status. Boot fails loudly on a duplicate ID or missing field.How Claude Code proves it is betterThe test is completeness against reality, not against itself. Script: feed the registry to a fresh agent session, then run doc 03's parity checklist and the missing-100 list from doc 15 as question sets ("can you dispute a charge?" "can you find unclaimed money?"). Every question must map to exactly one registry ID with a truthful status. Baseline: the pre-registry agent answers from the model's own impression and will both overclaim and underclaim; log both error types. The registry wins when mapping coverage is 100 percent and status answers match ground truth.Previous: Operating ModelNext: Parity SpecDraft specification.
