Upmore Spec 01: Agent Operating ModelHow the best agentic finance agent operates: the loop it runs, how it decides, when it acts alone versus asks, what it remembers, and when it stays silent. Everything else in this series plugs into this model.GoalBuild the core agent runtime: a loop that ingests financial events and user messages, decides what (if anything) to do, acts within a strict autonomy policy, verifies its own actions, and remembers what it learns. This is the skeleton every capability in doc 02 hangs off.The loopEvery wake, whether triggered by a user message, a connector event, a schedule, or a news signal, runs the same seven steps:1Observe. Pull the new inputs: the message, the transactions that just posted, the balance change, the bill that appeared, the news item, the calendar context.2Understand. Classify the input against the capability registry (doc 02). Resolve entities: which account, which person, which bill, which holding. Retrieve relevant memory.3Decide. Choose one of: answer, act, ask, watch, stay silent. The decision policy is below. If acting, pick the exact capability and its required inputs.4Gate. Check the autonomy tier for that capability (below). If the tier requires confirmation, compose the confirmation instead of acting.5Act. Execute through the capability's connector calls only. No capability acts outside its registered connector surface.6Verify. Read back the result from the source of truth (the connector, not the agent's own assumption). A send is not done until the rail confirms. A cancellation is not done until the merchant confirms or the follow-up check runs.7Remember. Write structured memory: facts, preferences, commitments, outcomes, corrections. Then compose the user-facing message per doc 11.The loop is a state machine, not a prompt. States: IDLE, OBSERVING, DECIDING, AWAITING_CONFIRMATION, ACTING, VERIFYING, FOLLOW_UP_SCHEDULED. Persist the state so a crash mid-send never double-sends or loses track. Every transition is logged with inputs and outputs; that log is the audit trail (doc 14) and the eval corpus (doc 12).Autonomy tiersEvery capability in the registry carries a tier. The tier is part of the capability definition, not a runtime guess.T0 Inform: answer questions, explain, report. No side effects. Always allowed.T1 Watch: monitor and alert. Balance dips, large transactions, bill increases, news on holdings. Always allowed once the user set the watch or the watch is a default the user can turn off.T2 Draft: prepare but never send or commit. Draft the cancellation email, stage the dispute, prepare the payment. Requires user approval of the exact final content and destination.T3 Act with confirmation: execute after the user confirms the specific action, amount, recipient, and timing. Sends, transfers, cancellations that take effect, order placements. The confirmation message must restate amount, recipient, destination account, fees, and timing in plain words.T4 Act within standing limits: execute without per-action confirmation inside a user-granted envelope. Examples: auto-move $50 to savings when checking exceeds $3,000; pay the electric bill up to $300/month. The envelope is explicit, user-set, revocable, and every action still gets a receipt message after the fact.T5 Never autonomous: anything irreversible, regulated, or novel. First-time recipient, first-time rail, anything above the user's envelope, anything the compliance layer (doc 14) flags. Always asks, every time.Tier assignment follows one rule: the cost of a wrong action decides the tier, not the frequency of the request. A $3 coffee subscription cancel is T3 (merchant side effects). Reading a balance is T0.Decision policyWhen inputs arrive, decide in this order:1Safety: does anything look like fraud, a scam, or an unauthorized change? If yes, alert immediately at high priority. This beats every other rule.2Direct request: did the user ask for something? Do that. Do not also do three adjacent things they did not ask for.3Commitments: is something the agent promised coming due (follow-up on a dispute, a bonus deadline, a scheduled rent check)? Handle it.4Standing watches: did a watched condition fire (threshold, due date, price, news match)? Notify per the watch's policy.5Proactive opportunities: did the save or earn engine find something worth the user's attention? Apply the proactivity budget below before speaking.6Otherwise: stay silent. Silence is the default. A finance agent that talks too much gets muted, and muted is dead.Proactivity budget and silence rulesNon-urgent proactive messages: at most one per day, at most four per week, unless the user asked for a cadence (morning brief) or the item is time-sensitive with a real deadline.Urgent (fraud suspected, overdraft imminent, payment failed): immediately, any hour, with the urgency stated in the first line.Never batch nagging. One message, the most important thing, with the option to hear the rest.Every proactive message must carry its reason: "you asked me to watch this" or "this saves you $18/month." If the agent cannot state why the user cares, it does not send.The user can turn any category off with one word, and the agent records it and never relitigates.Memory modelFour stores, all structured, all inspectable by the user on request:1Facts: accounts, balances history, bills, payees, holdings, income cadence, rent amount and due date, tax filing status as stated. Each fact carries its source and as-of time.2Preferences: risk comfort as stated, notification cadence, quiet hours, autonomy envelopes, tone preferences, which categories are muted.3Relationships: people the user pays or splits with, landlords, employer, advisor, with handles and history.4Outcomes: every action taken, its result, and any user correction. Corrections are the highest-value training signal (doc 12) and must be stored verbatim with the action they corrected.Memory writes are part of step 7 of the loop. Memory reads are part of step 2. No capability keeps its own private memory.Knowing what to sayResponse composition is fully specified in doc 11. The operating model's requirements on it:Answers lead with the number or the decision, then the reasoning in one or two lines, then the source and as-of time for anything factual about money.Every claim about the user's money is grounded in connector data with a timestamp. "Your checking is at $4,212.08 as of 2:14 pm" beats "your balance looks healthy."If data is stale (connector sync older than the freshness bar in doc 04), say so in the same sentence.If the agent does not know, it says so and says what it would take to know.Error handlingConnector failure during read: answer with the last good data, labeled with its age, and note the connector is down.Connector failure during a write: stop, do not retry blind. Money writes retry only with idempotency keys; if confirmation of the first attempt is ambiguous, the agent treats the action as unknown, tells the user exactly that, and reconciles before any second attempt.Ambiguous instruction: ask. The fill-the-gaps rule: act on a confident fill, ask on any gap where a wrong guess costs money, reaches the wrong person, or is hard to undo.Conflicting data between connectors: report both, prefer the source of truth for that data type (doc 04 ranks sources), never silently merge.Build packet for Claude CodeContext: this is the first thing in the repo.
