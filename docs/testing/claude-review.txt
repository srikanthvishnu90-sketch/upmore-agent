Reviewing the three files as given, with no tool access and no assumptions about the SQL RPC bodies.

## Actual defects

**1. Save idempotency is opt-in, so a plain retry creates a duplicate bill.**
Path: `supabase/functions/_shared/workflow_service.ts`, the `save` branch.
Trigger: `uuid(body.entry_id) ? body.entry_id : crypto.randomUUID()`. A client that retries after a network error without resending the same entry ID gets a fresh source key and a second row.
Impact: duplicate obligations inflate known-due cents, which feeds the affordability check in `plan` as other obligations. The comment promises idempotency the code does not enforce.
Test: call save twice with the same body and no entry ID, assert the second call either rejects or returns the first row, and assert exactly one obligation row for that user.

**2. A successful save retry fails once the bill's status moves.**
Path: same branch, the material-fields comparison.
Trigger: `materialKeys` includes `status` and `evidence`. If the row later becomes partially paid, settled, or gains evidence via another path, a delayed retry with the same entry ID throws "already used for different bill details".
Impact: the client sees an error for an operation that succeeded. The natural recovery is a new entry ID, which produces defect 1.
Test: save with entry ID, update the row's status to settled, retry the identical save, assert it returns the existing row rather than throwing.

**3. Plan's in-flight list does not match the attempt lifecycle.**
Path: `packages/domain/36-agent-workflows.js`, `plan`, the attempts check.
Trigger: the list is `reserved, submitted, processing, settled, unknown`. The payment service marks attempts via `agent_payment_uncertain` and its comments name an `uncertain` status. `runPaymentAttempt` treats only `applied, failed, returned, cancelled` as terminal.
Impact: an attempt in `uncertain` state is invisible to the planner, which produces a new proposal for the same bill while the original may still clear. This is the classic double-payment path.
Test: with one attempt in status `uncertain`, call plan and assert state is `monitoring` with code `payment_in_flight`. Define the in-flight set as the complement of the terminal set and reuse it in both modules.

**4. Reserve does not re-check in-flight attempts or proposal expiry.**
Path: `supabase/functions/_shared/payment_service.ts`, `reserveReviewedPayment`.
Trigger: it checks task state and hash only, then calls `agent_payment_reserve`. Two plan calls on one obligation create two tasks with different hashes because `expires_at` changes each call. Approving both and reserving both passes every check in this file. `validateConsent`, which enforces `expires_at`, is never called anywhere.
Impact: two reservations for one bill unless the reserve RPC has a partial unique index on non-terminal attempts per obligation. That guarantee is not visible here.
Test: plan, approve, plan again, approve, reserve both. Assert the second reserve returns the first attempt or a blocked state. Separately, approve a proposal, advance the clock past 15 minutes, reserve, assert rejection.

**5. Lookup miss on a settled attempt reports "settled" after downgrading it.**
Path: `payment_service.ts`, `runPaymentAttempt`, the empty-lookup branch.
Trigger: when `adapter.lookup` returns null, the code calls `agent_payment_uncertain` unconditionally, then returns `state:"settled"` if the attempt was settled.
Impact: the stored status regresses to uncertain while the caller is told the payment is settled. That is a false-completion signal to the queue and any UI.
Test: attempt in status settled, adapter lookup returns null, assert the returned state is not settled and the stored status equals whatever `agent_payment_uncertain` wrote.

**6. Record-event runs without the lease token.**
Path: `runPaymentAttempt`, the final `agent_payment_record_event` call.
Trigger: the claim lease is 45 seconds. A slow submit can outlive it. A second worker then claims, looks up, and records. The first worker's later record call carries no lease, so the RPC cannot reject it.
Impact: an older submit response can overwrite a newer provider status.
Test: simulate two workers where the first records after lease expiry, assert the RPC rejects the stale write when the lease is passed and verified.

## Launch prerequisites, not defects in this code

- **Execution is fully disabled today.** `EXECUTION_ADAPTERS` is empty, so `paymentPlanningContext` reports coverage incomplete and `plan` never reaches a proposal. Defects 3 through 6 become live only when the first adapter is registered.
- **Reserve and begin-submission RPCs must enforce** one non-terminal attempt per obligation, a matching obligation revision, and snapshot expiry. None of that is verifiable from these files.
- **Confirm-candidate passes every normalized field** including provider account, reference, and funding account to its RPC. The `edit` branch whitelists seven fields. The confirm RPC should whitelist the same way.
- **The planning `plan` call accepts a bill 48 hours old** by observed time. User-entered bills have no refresh path other than edit, so verify the edit RPC resets observed time or users will be told to refresh a bill they typed themselves.
- **`outcome` requires a matching provider payment ID** on the attempt. The first submit event has none to compare, so the record-event RPC must assign it before invoking this logic.

Fixes for 1, 2, 3, and 5 are contained in the two TypeScript files and the domain module. Fix 4 and 6 need the SQL side as well.
