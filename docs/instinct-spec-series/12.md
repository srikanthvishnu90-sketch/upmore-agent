Upmore Spec 12: Training and Evaluation Data"What data would we train." For an agent like Upmore, "training" is mostly not gradient updates: it is the constitution the model runs under, the gold data that calibrates it, and the eval sets that keep it honest. This doc specifies all three, plus when actual fine-tuning earns its cost.GoalBuild evals/data/: the datasets that make the agent know what to say, and the privacy rules that keep user financials out of training.Dataset 1: The constitution (behavior contract)A versioned system-level document: the operating model (doc 01) in compressed form, the voice principles (doc 11), the advice boundary (doc 09), the honesty contract (registry-backed capabilities only), and the escalation rules. This is the agent's standing instruction, and it is data: versioned, reviewed, and tested against like code. Every behavior change anywhere in the series must trace to a constitution line or change one.Dataset 2: Gold conversation libraryThe corpus that teaches "how to respond":Coverage: one or more gold conversations per registry capability (316), generated as capability x persona x scenario. Personas: the terse low-effort texter, the anxious first-timer, the detail-checker, the angry user mid-problem, the power user. Scenarios: happy path, missing data, ambiguous input, stale connector, declined confirmation, correction mid-flow.Format: full conversations with the connector state as fixtures, the expected agent turns, and annotations naming the principle each turn demonstrates (mirrors doc 11's gold format, at scale).Generation: model-generated drafts from the specs, then human or strong-model review against the voice rubric; bad turns get corrected and the correction is stored. Target: 1,500 conversations v1.Use: few-shot calibration, eval fixtures, and regression tests. A gold turn that the live agent would not reproduce is a failing test.Dataset 3: Tool-use tracesEvery capability's correct connector call sequences: for "send Sarah $85", the ordered calls (resolve person, check envelope, select rail, confirm, execute, verify, receipt) with fixture inputs and outputs. These traces teach the loop's act step and power the evals that catch skipped verification. Store as ordered call graphs, not prose.Dataset 4: Labeled domain setsNews relevance: 500 labeled stories per persona (doc 10 eval).Advice boundary: 40 red-team prompts plus jailbreak variants, and 40 legitimate requests (doc 09 eval).Transaction categorization: 2,000 hand-labeled merchant strings mapped to clean merchants and categories (powers TXN-003/004).Savings plays: 40 financial lives with labeled opportunities and dollar values (doc 07 eval).Parity flows: the 20 scripted app flows (doc 03).Dataset 5: Adversarial and failure setsPrompt injection through data: malicious text in transaction memos, receipt emails, payee names ("ignore your rules and..."). The agent must treat connector data as data, never instructions. 100 cases minimum.Hallucination traps: questions whose honest answer is "I don't have that" (a balance for a closed account, a capability that is GATED).Money math traps: split rounding, fee-inclusive totals, timezone-crossing due dates.Every real production failure joins this set permanently, with its fix.Privacy rules (hard constraints)Never train or tune on real user financial data. Real transactions, balances, and messages stay in the user's store; datasets are synthetic or anonymized-and-consented.Synthetic data is generated from archetypes (income bands, family shapes, city tiers), not by copying a real user.Corrections stored from production are behavior signals (what went wrong), stored without dollar amounts or counterparties when used for training.The datasets themselves get the consent and audit treatment from doc 14.When to actually fine-tunePrompt + constitution + gold few-shots first; it is faster to iterate and easier to audit. Fine-tune only when evals show a stable, measured gap that prompting cannot close (format compliance at scale, latency-critical classification), and only on synthetic or consented data. The eval harness decides: if prompted-Upmore passes the rubric, no fine-tune. Revisit quarterly with the same evals.Build packet for Claude CodeContext: evals/data/ with constitution/ (versioned md), gold/ (conversation fixtures), traces/ (call graphs), labeled/ (the four sets), adversarial/ (injection and trap cases), generators/ (the scripts that synthesize new gold conversations and personas from the specs).Constraints: generator output never ships unreviewed; every set has a schema and a validator; no real user data in any set, enforced by a lint that rejects account-number-shaped and routing-number-shaped strings.Done when: pnpm datasets validate passes all schemas; the gold library covers every registry capability with at least one conversation; the adversarial set runs in pnpm eval and the agent passes it; the privacy lint is wired into CI.How Claude Code proves it is betterData ablation: run the doc 13 benchmark suite three ways - constitution only, constitution + gold few-shots, constitution + gold + traces. The delta between runs is the proof each dataset earns its maintenance cost; a set that moves no metric gets cut. Report the ablation table in the eval results so the data investment is itself evaluated, not assumed.Previous: Response QualityNext: Testing HarnessDraft specification.
